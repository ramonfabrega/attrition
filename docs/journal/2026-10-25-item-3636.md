## Which side acted, and why

**Theirs struck the Library; ours never reached it.** The launch was 3634's hypothesis. It decides nothing:

- `678652`..`67867f` puts the walk's centre at the launch–landing midpoint only for a unit shooter whose type has
  `unit_flags & 0x2000`. That is the letter `n`, "destroyed when it attacks".
- The Bombard's `FLAGS` are `jr`. So the centre is the landing in both, and the launch feeds only the hit's angle.

**The cell.** The walk starts at spiral entry 0 and loops on `i <= radius[k]`. The listing has `incl`, `cmpl
0xadd1e0(,%ecx,4)` and **`jle`** at `678b45`..`678b50`.

Read from the PE (`.rdata`):

| table | value |
|---|---|
| `radius[0..10]` | 1, 9, 25, 49, 81, 121, 169, 225, 289, 361, 441 |
| entry 9 | (−1, −2) |
| entries 25, 49, …, 225 | (−(k+1), −(k+1)) |

The first `radius[k]` entries are exactly the Chebyshev square for k ≤ 7. So the walk reads **one cell more**, the
first cell of ring `k + 1`. The round's `k` is 1, the landing cell is (6289/768, 6920/768) = (8, 9), and the extra
cell is (7, 7). `Object::add_to_world@0064d8c0` chains an object into the one cell at its position, and the Library
sits in (7, 7).

Ours filtered candidates by the Chebyshev square alone (`Sim::land`, `combat::splash_cells`). This was already known:
**parked 3356c** (item 3356's sweep) names it, and left `Sim::land` unfixed because "a pinned diff could move".

**The count.** The building arm gives `dx = max(0, 241 − 5·192) = 0` and `dy = 1064 − 960 = 104`. Then `d` is 104,
the count is `256 − (104 << 8) / 192` = 118 ≥ 0, and the splash is 1: a fringe wound, the Library's first, and the
`% 100` draw at index 5.
