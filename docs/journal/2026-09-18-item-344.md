## 2026-09-18 — item 344: the mine does not survey the ground, it takes the mountain (Opus 5)

The brief called 8382 "a loop bound or an exit predicate, not an arithmetic
slip". It was an exit predicate, and it was not in the loop: it was in
`blocked_site`, one call down.

**Two numbers, one cause.** The frame is 46 draws against 865, and the fold
says the whole gap is two rows:

```
   3 Leader::make_stuff+0x221          ours 3
   9 Leader::produce_building+0xc99    ours 18
   4 Leader::produce_building+0x1805   ours 4
 828 Build::find_gather_tiles+0x10a    ours 0
   2 Leader::make_stuff+0x63d          ours 2   … and the rest agrees
```

828 is `4 × 207`, and `Build::find_gather_tiles`'s shuffle spends four draws
a tile. So the frame is a **mine** — Great Lakes' first, `1/2021` — and the
crate was both walking twice as many candidate cells and giving the mine an
empty mining list.

### The widening, and what it ruled out first

`RON_DBG_PLACE` (a scratch probe on `produce_building`, reverted) printed
every one of the spiral's 145 indices with its cell, its `check_building_wcoord`
class, its friend count, its score and the reason it broke. Eighteen
friendless candidates drew; the original drew nine; the stride never engaged
on either side, so the two walked the same 145 cells and the difference was
per-cell.

`RON_DEBUG_BUILDS` was widened to print each building's **position** and
`gather_from` length — and that is what ruled out the obvious causes in one
run. At 8381 all 28 buildings stand on the original's own coordinates and
the three camps carry 82, 61 and 104 tiles, which is exactly what run97's
frame 8382 says. So `find_friends`, `check_building_wcoord`, the territory
and the gathered-from map all had identical inputs. The difference had to be
in a predicate's *shape*.

### The predicate

`BuildTypeData::calc_gather@00639e40`'s head:

```
if (!is_flat(this) && !is(0x1a4) && !is(0x1a3)) { … the circle walk … }
```

A **mine never takes the survey**. Its arm is
`MountainsData::find_nearest@0089cd30` — the nearest mountain *tile*, in
world units, over every placed range — refused outright when the distance
exceeds `gather_radius * 0xc0`, which for `MINE_RADIUS` 6 is 1152. This
crate was running the camp's cell walk for it, which qualifies a cell when
its **centre tile** is a mountain inside six tiles of the anchor. That is a
much wider net.

Computed over the eighteen candidates the probe printed, the nine whose
nearest mountain tile is inside 1152 are i20, i25, i51, i53, i80, i83, i85,
i123 and i125. Nine. The other nine sit at 1269–1827.

### The list, and a capture nobody had opened

The value oracle turned out to be already on disk, twice. `grep -c '^ *mtn
[0-9]'` over every archive found eight files with a mine that has a range,
and among them **`gamelog-run97-greatlakes-valuewindow.txt`, the Great Lakes
window over `[8030, 9349]`** the capture lane landed the same morning — it
spans this map's word, and no test reads it. Its frame 8383 carries the mine one
frame after placement:

```
o 2021  who 1  pos 41088 25920  mtn 6  cliff -1  length 207
```

and 207 `tx`/`ty` pairs. run80, which the suite already loads, carries the
same 207 unchanged 15,600 frames later, so the cheap file is enough and the
616 MB one stays out of the gate.

`BuildTypeData::find_gather_tcoords@0063bdc0`'s metal arm takes the range's
tiles whole, keeping each that is not `SURFACE_FOREST`, stands on friendly
or unclaimed territory, and is not already gathered from.
`sim::Sim::mountain_range` rebuilds a range as the **eight-connected
component of mountain tiles** around the nearest one. On Great Lakes that
component is **244** tiles, of which exactly **37** carry `SURFACE_FOREST`.
244 − 37 = 207, and every one of the original's 207 is in it. The second
mine, `mtn 0`, agrees too: 232 for 232, on a range the reconstruction was
not fitted to.

`MountainRangeData::gather_size@0089d170` was read alongside, because it
settles what the *cells* are for: `solid_mount_wx`/`_wy` is the range's cells
whose own `WData.flags & 0x20` is clear and whose centre tile is a mountain —
sixteen of them here — while the size rung comes from `mount_tx`, the tile
count. The old reconstruction conflated the two.

### The value diff

- `great_lakes_first_mine_lists_its_mountain_range` (`rondata::diff`) walks
  run53's game to 23,999 and compares both mines' `gather_from` against
  run80's own `MiningList` **as a set**: 207 for 207 and 232 for 232, every
  tile shared. The set and not the sequence, and the test says why — the
  dump's order is the shuffle's, and the shuffle reads the order the map
  generator's template produced, which a component walk has no way to know.
  The **count** is what the sync stream sees, and the count is asserted.
- `Log::frame_builds` gained a fallback to the ordinary `FRAME` block: run80
  writes `BUILDS` per frame without `DUMP_ALL`, so nothing was nested under
  a `FULL DUMP` and the method answered empty on a file that plainly has the
  records.

### What this does not establish

In `docs/ECONOMY.md`, "The mine's range", five things, each with the capture
that would refuse it: the range **index** (`mtn 6` is the generator's
ordering and a component walk has none), the **pre-shuffle order** and so
the post-shuffle one (the count and the set are right; which tile a miner
works first is not), the **cliff arm** (`CliffsData::find_nearest` wins when
a scary cliff is nearer, and neither scored map has one `OBJECT_CLIFF`
tile), the **tie-break** in `find_nearest`, and the **region filter**, which
cannot bite at six tiles and is not written.
