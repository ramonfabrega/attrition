## The cause

`LeaderData::wonder_mark` is one past the highest entry of the leader's
wonder list in use. `Wonders::init_wonder` raises it when a wonder
activates, and `close_wonder` walks it down. Under `create_buildings`'
wonder arm, an easy AI outside a wonder victory goes on only while it is
zero. This crate read it as zero. **So an easy AI builds one wonder, and
who=1 had built the Pyramids.** No packet (run244) was taken: the dump
printed the field.

`Sim::note_wonders` derives both writers off the buildings. It runs at
the end of the buildings' pass, which is where `Build::activate` runs, so
the mark lands on the same block the dump prints it. `build.rs` is not
touched. `diff::leader` compares the row now. Two unit tests, each made
to fail on the wrong rule first:

- the mark read as zero ("the mark closes the arm");
- the mark as a count rather than a high-water mark ("entry 0 clears
  under 1").

**777 does not close.** The Pyramids' own readers and
`Nation::pyramids`' writer are untouched. `already_built` (`type_avail`'s
refusal of a wonder anyone has built) is a sibling I found and did not
build: the mark closes the arm before it matters here.
