## What the reading settles before the take

- **"Bit 4" is the value 4, the action bit.** `Unit::update_action@0060a870:22-35` skips each `is_move` order whose
  `flags & 4` is clear, and each `CHANGE_FORM`. `add_group_move_order@005e4710:61-68` clears that bit when its
  thirteenth argument is 0. The DLL's `@form` is `QUEUE_NEW`, so only the standing re-form lays a group move with
  the bit clear: `action_form`'s recursion calls `action_move_to(get_loc_to, QUEUE_LAST, .., action 0, ..)`. A
  walking group's replay (`finish_insert`'s case `0x13`) passes action 1 (GOLDEN §22: `flags 5` on 742). So the
  "march" is the members' walk to their slots, and the leader's move ends at its own slot.
- **`Unit::work@0060d180:158-197`** reviews on `(frame + o) & 15 == 0`, before the dispatch. The action must answer
  vslot `+0x20` and not be type 9, and the head must not be type `0x12`. It must also either not be a group order,
  or be one whose `+0x94` record names this unit (`+4 == o`, `+8 == who`): the leader. The packable lineage is
  asked first (`type +0x2b8 & 4` without `unit_masks & 0x80000`).
- **`check_target_path@005e22d0`'s path to `:190`.** The target must be set and seen. For a building, the
  unit-target block is skipped. Then, in order:
  - `is_on_map`;
  - not in range of `orders_x/y` (the skipped move's point);
  - an attack-shaped order (`+0x18`);
  - not `max_range == 0` with a one-node path;
  - the target's `+0x1c`, `is_wallbuild`, clear.

  Then `update_order`'s head must answer `is_group` and the unit's group must be `>= 0`; then `is_moving_to`.
- **This crate's port** (`orders.rs`, `check_target_path_steps`) asks `target_is_building()` where the original
  asks `is_wallbuild`, and `check_target_path_review` returns on any group head (`m.group.is_some()`). So ours never
  reaches the arm on this staging, whatever the original does.
