# Item 471 — the group's location for a queued move

*2026-09-21, Opus 5. `docs/ORDERS.md` §17.*

## The brief, and how it was wrong in a useful way

The item came as **`1/28`'s `order:move.off_x` 120 against 648 on block
10235**, with item 465's reading — `Form::compute`'s slot table — attached
as the fourth hypothesis on a frame where the first three had all been
wrong. The commander's instruction was to treat it as a candidate and read
the cast first.

That was the right instruction and the cast dissolved it in twenty minutes,
for the fourth time on this block run. Two things fell out of the first
widening pass:

- **`off_x` is `x mod 0x300`** — `crates/rondata/src/diff/order.rs` says so
  in the comment right above the row — so the field the item was named for
  is the destination said twice and never a slot of its own. The item's
  title named a unit and a field, and the record named neither.
- **All six members part, and they part on 9340** — the window's *first*
  block, 895 before the frame the item is about. `firsts` keeps the block a
  key first parts on, so a row that has been wrong since the order was born
  never appears on the block where its consequence does. Reading the 10235
  set alone could not have found this; `RON_DEBUG_ROWS=1-11000` found it in
  one run.

## The geometry, before any reading

The six destinations, ours and theirs, are the same six points. This crate's
are a clean 3×2 grid on 144; the original's are that grid turned. The
cheapest possible check said so before a single decompiled function was
opened: second moment about the centroid **114,048 against 112,512**, and a
Procrustes fit putting the rotation at **72.1°** against a logged
`group_angle` of **74.67°** — the gap being the 24-unit snap the
destinations land on.

That is worth writing down as a method note. "Is this the same set rotated?"
is a two-line calculation and it converted a table of twelve numbers into
one number, which is what made the rest a search for a single scalar rather
than a re-derivation of `compute_dests`.

## Where the scalar comes from

`Group::compute_form` picks the angle from `dest − loc`. This crate's delta
was zero, because `GroupData::get_loc` answers the leader's own position and
`docs/ARMY.md` §12's probe sends the group **to** that position.

Two candidates, and the first was wrong:

1. **The zero-delta arm.** The listing has `angle = leader.angle −
   ((signed char)angles[slot] << 24)` and this crate had neither half of it.
   Real, missing — and **not the answer**: run19 covers the issuing frame and
   `1/40`'s heading there is `-1512964096`, where the order wants
   `890830848`, with no packed byte spanning the gap.
2. **The wrong location function.** `action_move_near` asks `get_loc_to`,
   not `get_loc`, for `QUEUE_LAST` (`00704990:361`–`364`), and `get_loc_to`
   goes through `UnitData::get_final_loc` — where the leader *ends up*. The
   probe queues the farm attack at `QUEUE_NEW` and the walk home behind it.

`find_angle(39133 − 2112, 21131 − 31296) = 890830848` **to the bit**, the
farm `0/2004`'s own logged position, through this crate's own integer
`find_angle`. Every other point within reach of the call — the leader's
trailing move, each of the other five members' — misses by a quarter-degree
or more.

## What saved a capture

run100 starts at 9340 and the order is born at 8186, so the frame that
decides everything is outside the headline capture. Grepping the disk found
**run19** (`window-8174-8192`), cited three documents away for a different
claim about this same probe. Its block 8186 carries all six of this crate's
positions **to the unit** and the leader's heading to the bit; its block
8187 carries the order as written. That is what turned "the crate's leader
heading must be wrong" into "the leader's heading is right and is not the
input", which is the step the whole item turned on.

The rule earned its keep exactly as written: grep the disk before booking a
capture.

## The one that looked like a regression

`great_lakes_8186_plans_the_probe_s_route_the_original_s_way` went red, and
its **own comment** explained why before I did: it had recorded that
`1/40`'s stack held 47 entries where the original holds 94, with "a queued
move this crate does not hold" sitting beneath. It holds it now — 94 against
94 — so the comparison, which takes the common tail, doubled in width and
the newly-covered half parts.

Not a regression: newly-compared ground, the same shape as every widening's
first run. The 22 parting entries are pinned as rows rather than a count
(`PROBE_PLAN_PARTED`), and they are worth their own line — **every one
shares the original's `x` and sits one or two cells south in `y`**, over
three stretches that each re-converge, on a route whose start and end agree.
That is the cost function's tie-break, which is to say it is the word's own
residue showing up 2,000 frames earlier. One open question now stands in two
places, which is a better position than one.
