(GOLDEN §3, point 5). All three went into `chapter6.cmd`'s header and were
committed as `bf981e6` before the launch.

- **`bird`.** `run_cmd`'s case 0x52 pushes `9` and `0x192`. The listing at
  0x7df1b1/0x7df1b6 settles the order: owner 9, type `BIRD`. §10 had them

  +0x51c`, raw. `add_air_patrol_order` then runs on the same point, the
  same pair of calls `Objects::process_all`'s sampling makes.

  - `parse_cmd` with `no_mouse` 0, through `TerrainOut::get_mouse_coords`
    (from the chat box and `process_chat`);

    own point.

  The tracer calls `parse_cmd(…, 1)`, so neither is reached. The object is
  `malloc(0x558)` in `System::init`, and neither its constructor nor
  `ConsoleWin::init` writes the field. So the cursor is heap. I predicted
  zero: the bird at (24, 24), patrolling the corner.

  owners 0, 1 and 8 only, with birds flying. So §10's first falsifier, "no
  `AIRPATROLORDER` block after 700", would have fired whatever happened.
  I restated it on the draw stream: a birth draw on 700, a seventh
  `think_bird` from 704, and the 704 sampling a pair short.
- **`add` and an aircraft.** Case 0x4d/0x4e is `find_nearby_spot` then
  `init_unit`, with no `WHERE` or age test. `find_nearby_spot:143` skips
  the terrain test for domain 2. `fighter` and `bomber` are exact TYPENAME
  matches, #239 and #254. The predicted seats were chapter one's captain's
  arithmetic: (888, 7800) and (2424, 7800).
- **`!ai off` and the Bomber.** Every who=1 unit carries `0x40000`

  and `go_to_city`, which the human's Fighter does not. The line still
  stages no order, which is all §10 needs. So I did not restage it, and

- **Fuel.** `Unit::process`: an air unit with `inside_up < 0` raises
