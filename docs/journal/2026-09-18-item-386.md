# Item 386 — the tie was never a tie

Rules track, Opus 5, its own worktree. The brief: break §18's tie-break with
evidence or land a sharper falsifier. **It is broken, with evidence, and the
code has it.** The golden word did not move — 617, value diff 618, residue
ours 6 / theirs 8, all unchanged — but the frame under it did, and the two
suspects the brief named were both innocent.

## The three checks, and what each returned

**Check 1, grep the dump — returned a correction, not an answer.** The check
as written asks for "a frame where a searching unit's `near_o` differs from
the target its order takes". There is no such frame, and there could not be:
`find_nearby_target` writes `near_o` under `if (dist < best_dist)` — it is the
**nearest** candidate, not the winner. The golden record's `1/6 near_o 7` says
only that `0/7` is nearest at 198. §18 had leant on it as a witness of
*searching*, which it is; as a witness of *choosing*, it is not. And chapter
one has exactly one searching unit, so the dump cannot price anything.

**Check 2, the listing — exonerated both suspects.** `00649701`–`0064970e`:
`movsbl 0x3d(%eax)` (`targeted`, confirmed at `ObjectData+0x3d` in the PDB's
own type record), `addl $8`, `leal (%eax,%eax,2)`, `shll $4` — `(targeted + 8)
× 48`, instruction for instruction. `00649718`–`00649731`: `movl $0x2aaaaaab;
imull; sarl $5` with the sign fixup, and `⌈2³⁷/192⌉ = 0x2AAAAAAB`, so the
divisor is 192 and nothing else. §12.2's two reading-only constants are right
as documented. Fifteen minutes.

**Check 3 — I did not run the capture the brief named.** Staging a tie between
units of different `BLOCK_RADIUS` would have produced a second observation of
the same shape, and the shape was the problem. What the frame actually needed
was the **search's own answer**, which no dump holds; `tools/trace`'s call
proxies read exactly that, and they had seven sites and no site in combat. So
run108 adds three — `find_nearby_target` to bracket one search,
`attack_dist` and `compare_target` for the two numbers the ranking is built
from — and re-runs chapter one over frames 614–618. Build to receipt, 28
seconds.

## What one bracket said

```
attack_dist o=8 = 288 · compare_target o=8 in_range=1 ai=1 =  2155
attack_dist o=7 = 198 · compare_target o=7 in_range=1 ai=1 = 10771
attack_dist o=6 = 339 · compare_target o=6 in_range=1 ai=1 =  2155
find_nearby_target max_dist=4608 add_order=1 cavarch=0 flags=0 = 7
```

**They do not tie.** §18's whole derivation — that a tie must be broken by
scan order and that neither order gives `0/7`, so a constant must be wrong —
rested on "`compare_target` returns the same `value` for three identical
undamaged hoplites". That sentence is false, and it was the one thing in the
paragraph nobody had measured.

The factor is 4.998, which is §12.3's out-of-range `/5`, and the surprise is
where the range test lives. At `0064f1ed`:

```
if (param_3 != 0 && !raiding && is_in_range(this, o, who, x, y, y, 0, NULL) == 0)
    v /= 5;
```

`param_3` is the caller's `in_range`. For a non-guarding aggressive unit
§12.2's range gate sets it to 1 **without testing anything** — and that is the
point: the argument is a *permission to test*, not a verdict, and
`compare_target` does the test itself. Each candidate's second, nested
`attack_dist` in the trace is that call showing through.

So the constant that decides the golden record's engagement frame is `0xf6`,
the HOPLITES reach item 384 landed one day earlier at a different site. `0/7`
at 198 is inside it; 288 and 339 are not. Under the old `0x66` reading all
three would have been out of reach, all three discounted, and the tie would
have been genuine — the two findings are one constant read twice.

## What this crate had

`if !in_range && !self.is_in_range(attacker, target) { v /= 5; }` — the
predicate inverted. The discount fired only when the *caller* reported out of
range, which for a unit attacker is never, so the three candidates came back
112,506 apiece and the unit-array scan order handed the pick to `0/6`.

One clause. Made to fail on purpose both ways: with the old reading the pick
assertion comes back `Some(Unit(58))` against `Some(Unit(59))`, and the value
assertion `[112506, 112506, 112506]`.

## What is still wrong, and whose it is

At the end of frame 617 this crate's `1/6` drops its target and takes a
`GROUP_ATTACK_TO`, and walks off the seat it just held. The original's holds
`(1368, 7992)` for the rest of the record. §12.4's "Hit" path says a unit
already attacking ignores the hit unless its own target is out of range, and
`0/7` is not — so the group should be deferring, not ordering. That is the
same gap as "only the captain searches" seen from the other side, and both are
in `docs/GROUPS.md` §13 now. `0/7`'s retaliation also lands one frame early:
the dump has `recharging 32` at dump-619, this crate at the end of 617.

## The instrument, which is the reusable part

`--callwin LO HI` and `--tracer-def NAME` are new pass-throughs.
`live_session.stage` wrote `callwin=0-END` into every `rontrace.cfg`
unconditionally and `unattended_capture.py` hard-coded `TRACER_DEFS`, so a
probe that wants four frames of proxy records and one extra define had no way
to ask. `RON_TARGET_PROBE` is opt-in and `tracer.c` `#error`s if
`RON_TURN_PROBE` is defined too, since both would claim call-site ids 8 and 9.
A capture with neither define is byte-identical to run101's.
