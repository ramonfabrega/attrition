## Row 93: the reload gate reads the order's target

The probe printed the reload gate's conjuncts for every unit on 4811, with the stream's seed. Theirs' idle falls
between the fourth re-search draw and ours' do_move, at seed `0x98159e0`. Of the gate visits at that seed, three were
recharging on a fresh order:

- `1/106`: order, aim and `combat.target` are all `2/88`.
- `1/107`: all three are `2/107`.
- `1/109` (TI 283, `FLAKGUNGERMAN`, land, `recharging` 22, anim 12): its **order** targets `2/101` (uid 139), while
  guy 0's aim and `combat.target` are both `2/58`.

`Unit::fight@005fd4d0:111`–`:121` reads the attack order's data (`get_order`, vslot `+0xcc`). It compares `+0x8`
(`o`) with guy 0's `+0x8e`, then `+0xc` (`whom`) with `+0x9f`, and returns quietly only when both are equal. Next it
tests `+0x9c` (the anim) against 0..3, and then calls `set_anim(CHAR_DEFAULT, 1, 1)`. Ours compared `combat.target`
with the aim instead. `1/109`'s copy still named `2/58`, so ours found them equal and spent no draw.

**The fix**: compare the order's `(o, whom)` with guy 0's aim, read as `(index, owner)`, which is what the guys line
writes at `+0x8e`/`+0x9f`. An order with no target asks for nothing, as before; that case is under §22.5.

theirs 17833. All 8 ammo ranges and both guys ranges that parted on 4812 now agree. 97 units ranges still part there,
against 100 before.
