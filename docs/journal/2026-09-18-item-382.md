# Item 382 — the ceiling is an overflow, and the gate is the met bit

*2026-09-18, Opus 5, worktree `worktree-att-382`. The word did **not**
move: Great Lakes stays at 9182. Four leader-record residues each gained
one row, deliberately — the row that names the cause.*

## What the item asked

§44 left one thing open with a falsifier attached: this crate writes
`6,600,000` into `1/MAKE[0].val` on blocks 9179–9180 where the original
writes `9,999,999`, and `200 × 43,200 = 8,640,000` is not the ceiling, so
"name the path that reaches it". The falsifier it named was *anything
that puts this crate's value at 9,999,999 should move the word*.

Both halves are now measured. The path is named. The falsifier was run,
and **it is false** — the thing that closes the value costs 2,000 frames
of word rather than gaining any.

## How it went

**Twenty minutes of instrumentation beat the hypothesis, again.** Rather
than read `research_techs`, I put an `eprintln!` on `tech_value`'s tail
and replayed Great Lakes to 9199. Thirteen lines came out, one per census
sweep, and they said the whole thing:

```
8978  pre=132,000     income=64  val=33,000     cap=50 epop=39
9178  pre=26,400,000  income=64  val=6,600,000  cap=50 epop=42
```

`income` is `0x40`, a quarter — not 256. So the tail is not a scaling that
happens to land where it lands; it is a 32-bit multiply with a cliff at
`val > 33,554,431`, and the original's 34,560,000 is *just* over it while
this crate's 26,400,000 is under. The `9,999,999` is the original's own
`val < 0` guard catching a wrapped sign. That is the answer, and nothing
about it is a saturating multiply.

The ×200 the item's title leans on is real and is **upstream and on both
sides**: `base ×= 10` for knowledge in hand, and the cat-0 arm's `×= 20`
when `cap × 5 / 6 < effective_pop`, which is `41 < 42` and first true on
the rebuild frame. The original takes both too.

A second probe printed the weight vector and both arms of the war term:
`w_peace = 110`, `w_war = 144`. 110/144 is 55/72 — §43's ratio for four
techs and §44's for this one, and 26,400,000 × 144 / 110 is 34,560,000 to
the digit. One term.

## The part that was worth the day

Removing the `human` skip §43 blamed makes the census facts right and the
word **worse**: 9182 → 7182, with both loops and with the region loop
alone. So I went and greped the writers, which is what CLAUDE.md says to
do and what nobody had done for this field.

`treaties[i] & 1` is the met bit. `Leader::treaty_on@006e1190` sets it on
both sides; its only caller is `Leader::meet@006e1250`; `meet` has two
callers, `Wall::check_ever_seen@0063ce70` (fog) and
`Unit::process_attrition@005e11a0` (twice). And the dumps on disk already
held the answer — four windows of the *same game*, none of which had ever
had this field compared:

| block | `diplos[0]` | `treaties[0]` | `active_wars` |
|---|---|---|---|
| 6950, 7514 | 0 | **0** | 0 |
| 8174, 9170 | 0 | **1** | 1 |

**The diplomacy never moves.** They are at war the whole time. What moves
is contact, once, somewhere in (7616, 8174]. The `human` skip was never a
rule about humans — it is a stand-in for a bit this crate has no way to
set, and on a one-human-one-AI capture it is 2,000 frames closer than the
alternative. It lives in `Sim::met` now, with the measurement beside it.

Before believing the fog was the only route I checked the other one: over
run53's 24,000 frames, **no unit of either leader ever reaches a
non-exempt attrition outcome**. Zero. So the attrition path cannot be
what flips it here, and the successor is a visibility model rather than a
line in `attrition.rs` — which is worth knowing before anyone spends a
day on the cheaper-looking half.

## What I would do next

The met bit is the takes-chain to 9182 and it needs first contact, which
needs the "ever seen by" mask. `check_explore` is already a seam for the
same missing model (§2.1), so there is one mechanic behind two seams and
a value diff waiting on the other side of it.

The cheaper thing beside it: `income`'s own `0x40` is read off this crate
and the record does not print it, so the cliff's position rests on our
`check_income` being right. If it is not, both measured values are wrong
by the same factor and the 55/72 check would not notice.
