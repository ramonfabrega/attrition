### Two things settled it, and only one of them needed the screen

**The listing, in a minute.** `llvm-objdump -d --start-address=0x70e030`
gives both pairs outright:

- arm 1 (`70e109`–`70e12d`): `vector_dist(leader − (ox, oy))`, and on
  success return `(ox, oy)`;
- arm 2 (`70e190`–`70e1bc`): `vector_dist(order − (ox, oy))`, and on
  success return `leader − order + (ox, oy)`.

Both compares are `cmpl $0x180` then `jg`, so **both bounds are inclusive**
and `docs/GROUPS.md` §6.3's two different spellings (`0x181` and `0x180`)
were always the same set.

And one name was wrong in the document. Arm 2 calls the order's vtable
`+0xb8` — `MoveOrder::get_move_order` — and reads `[+4]`/`[+8]` off the
result. The type record names those **`x`/`y`**, the order's *destination*;
`orig_x`/`orig_y` are at `+0x44`/`+0x48`. §6.3 said "its current move's
origin". The surrounding code reads identically either way, and on the very
block that settled this the two fields hold the **same pair**, so neither
the decompile nor the dump could have caught it. A name is settled by the
type record, never by the surrounding code — the audit README's line,
earning itself again.
