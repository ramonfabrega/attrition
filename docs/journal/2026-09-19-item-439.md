# Item 439 — the eight bytes were innocent, and already written down twice

*2026-09-19, Opus 5, `worktree-att-365`. A short item, and short is the
honest size. No capture, no score moved, `crates/sim` untouched. The
product is a correction to my own §28.2 and a seventh entry on §28.4's
list of things now known not to be the answer.*

## The blast radius, named before resolving it

The brief asked for that first, and it is the step that made the item
five minutes rather than an afternoon. Grepping `docs/` for the array's
element size turned up four dependents — and **two of them already
contained the answer**:

- `docs/ANIM.md`: "`Leaders::list` is **`Leader[10]`**, `sizeof(Leader) =
  0x6eec`", used as the stride and correct.
- `docs/AI.md`: "the PDB's `Leader` is a 0x6eec-byte shell over
  `LeaderData` (0x6ee4) and Ghidra did not populate it. `field_0xNNN` on a
  `Leader *` is a `LeaderData` field."
- `docs/ATTRITION.md`'s field table quotes `LeaderData (28,388 B)` — the
  inner type's own size, for a field offset, not a stride.
- `docs/ARMY.md`, `docs/CITIES.md` and `docs/AI.md` quote
  `leaders.list[who] + 0xNN` offsets.

So the question was never "what are the eight bytes" but "does anything
shift". It does not.

## Innocent, and I compared the wrong two types

`types.txt` gives `struct Leader // size 0x6eec` and
`struct LeaderData // size 0x6ee4`. The listing's `imull $0x6eec` is
`Leader`'s stride against `Leader`'s size — no disagreement at all. §28.2
set 28,396 beside `LeaderData`'s 28,388 and called it an eight-byte
difference; it was two different types.

And `LeaderData` sits at the shell's offset 0, which the listing itself
confirms: it reads `leader_flags` at `base + who × 28,396 + 0`, and
`LeaderData +0x0` is `leader_flags`. So every `leaders.list[who] + 0xNN`
in `docs/` is an unshifted `LeaderData` offset, exactly as `docs/AI.md`
already said.

## Stopped, because the brief said to

The eight bytes are innocent, so this is a seventh entry on §28.4 rather
than an eighth account. The bracket still has not moved — a melee searcher
on the zero path behaves as though its radius were
`unit_respond_range * 0xc0` with `unit_respond_range` 7 — and the space
around it is one candidate smaller.

The thing worth noticing is that **recording the difference rather than
smoothing it is what made this cheap**. Had §28.2 said "the stride is
28,396" and moved on, the wrong comparison would have been invisible and
the next reader computing an offset through that array would have had
nothing to check against.

## The trap, working as documented

`docs/audit/README.md` lists it: when the decompiler prints a local that
cannot be right, the listing or the PE bytes settle it in a minute. Item
437 hit it exactly — `*(byte *)(leaders.list + who) & 2`, a byte index
into a 28,396-byte element — and one `llvm-objdump` line showed
`imull $0x6eec` and settled the branch. The irony is that the same listing
line then produced this item's phantom, because a stride in hand invites
comparison with the nearest size you can find. The lesson is narrower than
the trap: **when a listing hands you a stride, the type to compare it
against is the array's element, and the array's element is what the
declaration says — not the type whose fields you have been reading.**
