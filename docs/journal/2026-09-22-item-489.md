# Item 489 — the soft arm asked the army where the original asks the group

*2026-09-22, lane att-489, Opus 5. Great Lakes' long word **10277 →
10294**; block 10278's seventeen rows to none.*

## What was booked, and what it turned out to be

487 left the word at 10277 with block 10278 holding seventeen rows —
sixteen `1/40`'s, one `1/41`'s. `1/40` collides with `1/41` here and the
original's does not. The seventeenth row was written deliberately as a
row and not a mechanism (`docs/DECISIONS.md` 42): the original sets
`unit_masks & 0x100000` on **both** raiders and this crate on neither,
and which way the arrow ran between that bit and `1/40`'s hard
`collide_o 41` was the successor's to establish.

The brief said to treat the title as something to kill. It survived —
but not as two threads. The flag and the collision are **the same arm
seen from its two sides**: `0x100000` is what §4.3's scan raises when it
calls a collision *soft*, so a block that raises it on both units is a
block on which neither hard-collides. There was never a second thing to
find.

## The order the evidence came in

**The widening first, before a line of decompile.** 313 keys over
`[9340, 10290]`, seventeen on 10278, nothing else on the block across 102
units, 28 buildings and 3 cities. The booking survived it.

**Then the position gate, which is the clause that mattered.**
`docs/COLLISION.md` §8.4 compares `half_step` only where positions agree,
and the widening runs it ungated — so the question "is this row a real
measurement" had to be asked directly. `1/41 pos` first parts on
**10279**: on 10278 it stands exactly where the original's does, and its
`half_step` row is clean. `1/40 pos` first parts *on* 10278, which is the
frame a word is read on. Both readable, for different reasons. Had
`1/41`'s position parted a frame earlier the whole booking would have
been a different measurement.

**Then the dump, before any capture was considered.** `track.py` over
`unit_masks` for both raiders across `[10265, 10290]` — twenty seconds —
and it gave three things the section did not have: the bit is never set
on two consecutive blocks; `collide` is 0 and `collide_o` −1 on every one
of them, so the original never hard-collides in this window at all; and
the step *after* each flagged block is twelve where every other is
twenty-five. That last one is the first behavioural confirmation that
`0x100000` is a half step rather than merely a flag — `docs/MOVEMENT.md`
had it from a reading since item 219.

**Then the sweep, read from inside the frame.** §9.1's `SweepWatch` is
the instrument item 456 built for exactly this, and it needed no capture:
it records this crate's own `sweep_verdict` where the original's bracket
sits. `1/40` proposes `(2444, 31293)`, hits cell `(49, 650)`,
`will_be_corner` 1, walks to `1/41`, declines every soft arm, asks
`is_corner` (0), and refuses. `1/41` probes and finds **nothing** — which
is the row that named the cause, because it is only clear if `1/40` is
standing where it should have stepped. One arrow, two rows.

**Only then the decompile**, and it took one line.
`detect_unit_collision@00617060:307` is `this->+0x80 == other->+0x80 &&
!= -1` — a `short`, the `Groups::list` slot. `Sim::same_group_soft` asked
`Sim::army_of`, which answers `None` for all six raiders while the dump
says `group 65` for every one of the 951 blocks.

## The defect is a seam that outlived its own fix

`Sim::group_of` — "the original's `unit +0x80` read straight into the
pool" — is the resolver **item 465 built and item 470 measured**, and
`find_ordered_collision` has used it since. `same_group_soft` was the
site nobody moved over. Its doc comment still said "an army's members are
its group", which was true until item 465 gave this probe's six raiders a
real `GROUP_MOVE` in a pushed slot — and `push_group` takes its members
*out* of the army. From that day every member of a pushed group was hard
to every other, and a squad walking home stood on itself.

Two items had walked past it. 487 read the same block and named the two
`half_step` rows as a thread without asking what set them; 456 landed
`group_of` for a different consumer on the same arm's other clause. The
grep that would have found it is the one CLAUDE.md already asks for —
*grep this crate for the field before reading the original's writers of
it* — applied to `group_of` rather than to `group`.
