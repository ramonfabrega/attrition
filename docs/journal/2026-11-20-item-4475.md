## The writer that raises `0x20`

4472's grep found `| 0x20` on `Region::flags` only in `Build::close`. Its
filter was the spelling `0x88 + 8`. `World::compute_reg_territory@006b0bb0`
spells it `&local_40->field_0x8 + *regions`, with `local_40` = `r·0x88`
(`+0x14` is `size`, `+0x2c` is `borders`, by `types.txt`'s `Region`). At
`:280`–`282`, in the arm reached when `borders >= size`, it ors `0x80`
and then `0x20`. The listing has `orl $0x80, 0x8(%edi,%eax)` at `006b1a3d`
and `orl $0x20` at `006b1a47`, behind `cmpl 0x14, 0x2c; jl` at `006b1a0d`.
`GameDaemon::check_borders@00732060:23` calls the walk only on a region
with `borders < size`. So a region takes `0x20` once per fix, on the frame
the pass writes its last cell.

The direction: **theirs acted, ours did not**. Ours' `advance_border_pass`
(`crates/sim/src/territory/border_pass.rs`) raised the economy flag at a
region's end but not the region's bit. Ours' tick runs `cycle_gather_flags`
(`core/frame.rs:293`) before `check_borders` (`:299`), the same order as
`GameDaemon::process_all`. So a region finished on frame F verifies in F's
objects and re-walks on F+1.

The `0x80` feeds `Borders::add_border_region`, which this crate does not
carry, so it stays out. The pre-play wholesale pass is left alone, since
