## Where this departs from the pass's table, and why

The commander's word (15:45): the table is the design, not an order; four things hold. Departures so far:

- **Stages 1 and 2 are designed together.** The group unit's interface (what a process is told, what order its
  tests run in) depends on how a window resumes, and the evidence above says the windows are the bulk.
- **The groups come from a gate's own fixture audit, not from a rule on names.** No registry of tests exists;
  the audit already says which test reads which game. A test the audit never saw runs alone, so a stale file
  costs seconds and never a verdict.
- **"Ascending frame order" is not built.** libtest runs a filter's tests in name order and offers no other.
  The kept walk falls back to the state its last walk started from, as the coverage batch does. Whether name
  order is good enough is a measurement the work in progress exists to take (below).
- **The audit is held equal as a multiset, not as a set**, so the comparison is a strict equality: a cache's
  fill and a resumed stand-up are both credited to the reader.
