## 2026-09-18 — item 354: a clause that returns zero (Opus 5)

The brief said the widening names the mechanism and not the other way
round. It did, twice: the fold named a unit, the unit's own record named a
path, and the path named a cost term. No decompile was opened until the
dump had already said which function to open — and when it was opened, the
answer was not in the decompiled body at all. It was in the vtables.

### The fold named `1/27`, and the record named the route

Great Lakes 8663 is one extra draw: `Unit::do_move+0xe84`, the grid roll a
move pays when `find_path` refuses its straight line. `RON_DEBUG_FOLD`'s
attribution puts it on `1/27` — one of the four units item 352's journal
had left parked as "late drift from 8579, names no draw". It named one.

run97 covers `[8030, 9349]` and the widening is `UNITDATA` either side.
`1/28` and `1/29` part first, on 8579, and the part is three units of `y`:

| | 8578 | **8579** |
|---|---|---|
| ours | (27041, 26782) | (27012, **26786**) |
| theirs | (27041, 26782) | (27012, **26783**) |

Same `x` step, different `y` step, so the *heading* differed — and the
heading comes from the top of the path stack, which both sides pop on that
very frame. The original's new waypoint is `(25944, 26040)`; this crate's
is `(25944, 27576)`. One cell apart, and the whole stack had been sitting
there disagreeing since **8186**, 393 frames earlier, where
`Group::action_move_near` planned it. Nothing before 8579 could see it,
because a wrong waypoint costs nothing until a unit reaches it.

That is the case for widening the record rather than the field: the
position diff is a *consequence* four hundred frames downstream of its
cause, and the path — which the run97 test had never compared — is the
cause itself.

### Both routes cost 184, which is why the wrong one was reachable

The chains agree for thirteen waypoints, part for five steps, and rejoin:

Five steps and three diagonals on both, so on geometry they **tie** at
`5×32 + 3×8 = 184`. A tie is the interesting case: it means no cost term
separated them, and a term the original has and this crate does not would.

The cells said which. A probe over `x 27..36, y 31..37` of this crate's
own world at 8186 — flags, `blocked`, `solid`, `bad`, owner, `is_ocean`
and `danger_half` for both players:

- danger is **0** on every one of them, for both players, so §5's one
  dynamic term was never a candidate;
- (32, 35) carries `blocked 12` — the forest that keeps *both* routes off
  row 35 at `+240`;
- and the three cells this crate chose — (33, 35), (32, 34), (31, 35) —
  all carry **`flags 0x200`**, `NEARBLOCK`, while all five of the
  original's carry `0x0`.

`NEARBLOCK` is one of §5's two army terms: `base <<= 5`, 32 against
**1024**. With the `army` mode on, the original's route costs 184 and this
crate's 3160. With it off they tie, and the tie falls the other way.

run93's block 7932 had already put the whole western half of the map cell
for cell on the original's own scan, so the world was never in question
either. The mode was the only term left, and `RON_PROBE354` on
`find_wpath_from` printed it: `army false (hint false human false mode
false) … no_danger true`, for all six units, on frame 8186. Of
`army_mode`'s three terms — `armed`, `!worker`, `!attacking` — only
`attacking` was false-ing it.

### `is_attacking` is a `return 0`, in all seventeen order vtables

`UnitData::is_attacking@0060a5b0` is four lines of decompile and the
important one is `call *0x18(%eax)` on the **current order's** vtable, not
the unit's. This crate had read it as "the unit has a combat target",
which is a reasonable reading of the name and of nothing else.

Slot `+0x18` is `is_attack`: the only class in the export that declares an
override there is `AttackGroundOrder`, and `rise.pdb` names its thunk
`AttackGroundOrder::is_attack'vtordisp{-4,0}'@0048384b` — which is the
only reason the slot can be identified at all, because everything else
folds onto a stub. Ghidra's own vtable dump then shows `Window::get_button`
in that slot for every other order class, which is what COMDAT folding
looks like from the outside: a foreign name standing in for `{ return 0; }`.

Read straight out of `riseofnations.exe` — section table, VA to file
offset, four bytes at `vtable + 0x18` — all seventeen order vtables:
fifteen hold `0041bff0`, and `AttackGroundOrder`/`AirAttackGroundOrder`
hold `0048384b`, the thunk, which adjusts `this` and tail-calls
`0041bff0`. `0041bff0` is `return 0`.

So the clause cannot fire on any order the game can hold, `find_wpath` is
its only caller in the whole executable, and the correction is a deletion:

```rust
armed && !worker && !river
```

This is the audit README's most-repeated lesson arriving in its purest
form — *the arithmetic is doubly confirmed almost everywhere and the
predicates are where the errors are* — with a twist it had not had before:
the error was not in the decompiled body, which was right, but in what the
body's virtual call resolves to. A listing read would have found it; so
would the PE bytes, which is what did. Twenty minutes, after the widening
had already named the function.
