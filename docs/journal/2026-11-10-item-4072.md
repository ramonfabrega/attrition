## Loop 4070: the pins that read the tree go first

**What the row said, and what I measured.** The row reads that `diff::floors` runs 37 tests in release and
22 under `guard.sh`'s debug profile, with the shape pin among the fifteen left out. On `b1cd30b9b`,
`zsh tools/guard.sh diff::floors` runs **37** floors tests in debug, the shape pin among them
(`test result: ok. 37 passed; ... 2153 filtered out`). The only `22 passed` in that reflex's log is the line
before it, `cargo test -p rondata the_handoff`, which runs 22 tests. The floors module has no debug door: the
shape pin runs `python3 tools/shape.py` and reaches no dump. The filter loop has run `-p sim -p rondata` since
Loop 4040 (`11d6c9fb5`), which is in `4db10248d`. So I could not reproduce the fifteen. What does hold is the
row's real point: a builder's reflex reaches the shape pin only when its own filters name `diff::floors`, and
4063's builder ran `diff::start`.

**What moved.**

- `tools/shape.py --check` compares the tree's six counts with `STRUCTURE` as
  `crates/rondata/src/diff/floors.rs` writes it, and exits 1 naming each count that moved, with its delta. It
  takes 0.4 s and builds nothing. If it cannot read the pin, that is an error, never an empty pin that agrees.
  The Rust pin stays the authority and still runs in the release step.
- **The reflex** (`tools/guard.sh`) runs `shape.py --check` right after its offline suites, on every run,
  whatever the filters. After the blind list it runs the rest of the pins that read the tree and not a game,
  on the library the blind list just built: the structure pin itself, the field-writer guards (`writers::`)
  and the widening ledger (`ledger::`). That is 10 tests in about 6 s of debug. I chose both the python tool
  and the test. The tool holds the pin before anything is built. The test is the pin itself, at no extra build
  cost, so the two cannot drift apart unseen.
- **The gate** has a new first step, `pins` (`shape.py --check`, 2 slots / 1 GiB), and it stops the gate when
  red. The guard step (the blind list, the paperwork guards, `docs_guard`, the structure pin) now runs **before**
  the release step, so it is where the release test binaries get built. That makes it a build: it reserves
  8 slots / 32 GiB, as clippy and the survey do. The steps read
  `pins, offline, clippy, fmt, survey, guard, release`. The release step still runs every one of these tests.
  The closing lines keep their form, with the new name added: `Gate steps: 7 of 7 ran (...)`.
  `tools/gates.py` reads the release minutes by name, so the reorder does not touch it.

## Loop 4042: the bound on the `rondata` library

**The evidence.** The gate log `gate-d78-c.log` (on `dc1e1fd39`) closes with
`Gate minutes: offline 1.2, clippy 0.1, fmt 0.0, survey 0.1, release 49.9, guard 0.8`. Its report is
`attrition-gate-v93am7t9`, with `isolated/rondata/measurements.jsonl` (2,181 rows), `summary.json`
(2,519.1 s, CPU 9,965 s) and each test's log. A test's start is its log's birth time and its end the log's
last write. That span reproduces `summary.json`'s 2,519.1 s to the tenth.

- **Occupied share: 49.6 %**, 10,004 of 8 × 2,519.1 = 20,153 slot-seconds.
- **What an occupied slot did: compute.** CPU 9,965 s against 10,004 s of wall (0.996). By family the ratio is
  0.89–0.98, with `mapgen` the one above 1 (1.38, threaded). The runner's own overhead is 161 s in all, 74 ms
  a test. Admission waited 16.3 s in all, 0.15 s at most.
- **What an idle slot waited on: nothing; the queue was empty.**
  `diff::coverage::every_parsed_field_is_compared_by_the_instrument_or_pinned` ran from second 0 to second
  2,519.1 (2,156.6 s user, 254.5 s system, 1,364 MiB). The other 2,180 tests held 7,485 s. The last of them
  started at 1,068.6 and ended at 1,070.5: 6.99 slots beside the pin for 1,070 s, then seven slots idle for
  1,449 s (10,140 slot-seconds). The library was as long as one test.
- **The bound: that test's serial walk.** It walks 436 windows, one after another. On 2026-10-15 it walked 61
  and ran 202 s alone. That is the row `docs/audit/2026-10-15-suite-timings.txt` still carries, because
  `--stale-only` re-times only tests it has never timed. Every chapter adds a window. Its isolated ceiling is
  3,600 s (Loop 3681), and it stood at 2,519.
- **The park row's hypothesis is killed.** The estimated-RSS budget bound nothing: 16.3 s of admission wait
  over 2,202 leases, and all eight slots were held for the first 1,070 s. Doubling the budget would change no
  start.
- **The estimate's base was stale.** The 5,105 s "alone" sum is 9,995 s of slots in this gate (CPU 9,959 s).
  The pin accounts for 2,317 s of the gap. The 1,416 tests between 0.5 s and 5 s alone account for 2,467 s:
  3,171 s alone against 5,638 s here, with CPU close to wall. This gate cannot tell whether that is the
  verifiers, the load, or growth since they were timed. The library's real work is about 9,965 CPU-seconds,
  so on eight slots, fully packed, its floor is about 1,246 s (20.8 minutes), not the 17 the stale sum gave.

**What moved.** The walk runs on `RON_TEST_CPU` threads. Each takes the next run of one module's consecutive
windows, in order, under its own replay prefix batch and recorder. The registrations, mask words and skipped
keys are unions, merged after the walk. The walker threads carry the test thread's name, which is what the
fixture audit records. Every window is now one `w!(module::function)` line. The isolated runner reads a profile
row's `cpu: k`, reserves k pool slots and k host CPU slots, and passes `RON_TEST_CPU=k`; the head of the queue
starts when its width fits (FIFO). The coverage row is `cpu: 8, elapsed: 347.52, rss_bytes: 3109191680`. Red
first: the `Width` fixture in `tools/explore/test_isolated_tests.py` failed against the booked runner with
`{'a': 1, 'b': 1, 'c': 1, 'd': 1, 'wide': 1} != {'wide': 4, ...}`.

**Measured.** I ran the pin as the runner runs it (`/usr/bin/time -l`, shared budget, the whole gate's
`RON_VERIFY_*`), on this branch's release binary:

- **Eight walkers:** `test result: ok. 1 passed`, `347.52 real 2339.88 user 319.09 sys`, 3,109,191,680
  maximum resident, 52,653,607,248,829 instructions retired. The serial walk in the gate retired
  52,439,236,749,918 in 2,518.99 s. The same work, within 0.4 %, so grouping by module kept the prefix reuse.
- **Four walkers:** at a host load of 40 this was killed at my 600 s cap with no verdict (sampled peak
  1,803 MiB).
- **Before and after:** the pin went from 2,519.0 s to 347.5 s. Projected from the gate's rows: the library
  about 1,283 s (21.4 min) against 2,519 s, the release step about 29 min against 49.9, and a whole gate about
  31 against 52.1. The booking gate is the measurement.

The estimate to beat was "the work of five slots": about 17 minutes for the library and 26 for a gate. Its base
was the stale 5,105 s. On the real 9,965 CPU-seconds the packed floor is 20.8 minutes, and this lands about
0.6 minutes above it. The rest of the gap to 26 is the serial tail after the library: the sweeps 387 s, `sim`
64 s and the rest about 10 s, 7.7 minutes run one after another. Overlapping that tail with the library's last
minutes is the next scheduling move, and I did not build it.

**What is not established.** The whole-gate number is a projection. I also do not know why the mid-sized
tests ran 1.8× their alone time, or whether four walkers suffice on a quiet host. The rest of the isolated
profile is a month stale (876 rows for 2,181 tests, so 1,305 tests reserve the unknown 8 GiB), harmless while
admission does not bind. The timings table's coverage row (202 s) feeds only the lane skip list, and any value
over 1 s skips the test the same way.
