## The reading: what the game reads of the mouse

I read the input path before writing anything (the decompile export, `d3dgl.dll`'s listing, both import tables).

- **The executable never calls `GetCursorPos`.** It imports no cursor or message API at all (`GetAsyncKeyState`,
  `GetKeyState` and `MessageBox*` only). The window procedure belongs to the renderer DLL that
  `GraphSys::init_system@0054abf0` loads, `d3dgl.dll` (`get_graphsy_object_ptr`, its one export). That DLL is the only
  module importing `GetCursorPos` and `ScreenToClient`.
- **Door 1, events.** `bighuge_init_real@00539630` hands the renderer `Window::message_handler` (VA `0xebe4dc`, on
  `SysMessageHandler::vftable@00b64d18`). The window procedure (`d3dgl` `0x10012345`'s `WM_*` jump table) decodes
  lParam and calls the handler's slots: `OnMouseMove(x, y)` +0x14, `OnLButtonDown(dbl, x, y)` +0x20, `OnLButtonUp(x, y)`
  +0x24, `OnRButtonDown` +0x28, `OnRButtonUp` +0x2c. Each divides by `graphsys->screen_scale_x/y`, finds the window
  under the point (`Window::get_mouse_window`) and calls its `on_l_button_down` (+0x3f4) and the rest. The click test
  is capture plus the window's rectangle (`Window::on_l_button_up@00a54d40`), never a timer, so a down and an up in one
  call stack make a click.
- **Door 2, a polled position.** `graphsys` slot +0x38 (`d3dgl` `0x1000c4e0`) returns a cached pair at +0x460/+0x464.
  Slot +0x34 (`0x1000c470`) refreshes it: `GetCursorPos`, `ScreenToClient` on the window at +0x45c, divided by the
  scale. The refresh has one caller, `Window::update_cursor@00a502e0`. The getter has fifteen callers in the
  export, `Window::get_mouse_pos` among them. Which of them a hover or Loop 3432's tooltip reads, I did not establish.

**The shape, and why not posted messages.** The item's candidate was to post `WM_*` messages to the window and hook
`GetCursorPos`. The reading supports something narrower:

- A posted message lands on whichever pump turn runs next, a wall-clock frame. That is exactly the cost the queue lane
  pays, where a driven take parts its twin at its first click.
- A `GetCursorPos` hook would be an IAT patch in another module.

So `tools/trace/click.h` does three things:

1. It calls the original handler slots directly, at the top of the line's `do_frame`, like every other `@` line:
   move, then down, then up.
2. It swaps the renderer object's vftable pointer for a whole copy whose refresh slot writes the pinned point.
3. It swaps `message_handler`'s vftable pointer for a copy whose ten mouse slots drop the window procedure's own events.

Both swaps check the shipped bytes first: the getter, the refresh's `GetCursorPos` call, a scale of exactly 1.0 and
the handler's shipped vftable. They are installed at the first frame only when a click line or `rontrace.cfg`'s
`cursor=X,Y` asks, so every other capture runs byte for byte as before. Calling a `GroupOut` wrapper was ruled out by
the brief, and this is not that: the clicks go through `Window::get_mouse_window`, the command card's buttons,
`Options::exec`, `Options::picked_spot` and `Console::execute_at_cursor`, the whole UI predicate.

`unattended_capture.py` gains `--no-ffwd`. The pool schedules `37 !ffwd` whenever the end frame passes 37, and a pick
under the cursor needs a drawn scene (run47; 3427's stanzas are `ffwd: -`).
