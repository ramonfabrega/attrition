## 2026-09-17 — item 336: Great Lakes 8201 was a unit standing five units left of where the original put it (Opus 5)

The item was booked as a **widening and nothing else** — no open item named
8201's frame — with one candidate named (parked 333, `1/28`'s 41-entry path
stack) and the explicit warning that it was not the answer. It is not; it is
still parked.

**The disk first.** The commander's grep held: `gamelog-run19-window-8174-8192.txt`
runs to **8201**, not 8192. Its blocks are 8174–8191 and then one more, the
close-out dump the engine writes on quit — `BEGIN FRAME 8201` … `GameInfo
closing`. That last block is reduced (no orders, no `STACK<TYPE>`, no
`PATHDATA`) but it carries **`UNITDATA` for all ninety units**, which is what
made a value comparison possible on the word's own frame.

**The widening took one run.** `RON_DEBUG_SITES=8150-8230`, and fifty-one
frames below 8201 agree entry for entry:

```

  frame 8201: ours   5 theirs   4   — ours has one extra, at index 0
  frame 8202: ours   9 theirs  10   — theirs has one extra, at index 2
```

One draw, `Guy::set_anim+0x97a < Unit::move_step+0x823` — the blocked stand
(`docs/COLLISION.md` §5) — spent by this crate on 8201 and by the original on
8202. Everything else on both frames is identical. The attributed fold names
the unit without a hypothesis: **`1/42`**.

**Then the half the draw stream cannot do.** `1/42`'s positions, ours against
run19's, are exact from 8174 to block 8186 and then part — and the way they
part is the whole item. From block 8188 on, **both sides walk `(−11, +27)` a
frame, forever, with ours a constant `(−5, +9)` off.** A crate that walks the
original's own velocity from the wrong point agrees with the draw stream for
as long as nothing in the world notices, which here was fifteen frames.

The one frame in between is block 8187 — the end of sim-frame 8186, which is
`Army::find_target`'s probe frame, the one item 329 worked on. The original
moves `1/42` ten units **back** along a march it was walking at twenty-six a
frame, with its `angle` unchanged. This crate moved it not at all.

**Widening the cast answered what the one unit could not.** Of the probe's
six, three — `1/27`, `1/28`, `1/29` — do not move on that frame in either
build. The other three do, in the original only:

```
         block 8186        block 8187
  1/40   (39133, 21131) →  (39144, 21144)
  1/41   (36915, 23248) →  (36936, 23256)
  1/42   (36883, 23073) →  (36888, 23064)
```

Every one of those six coordinates is its own axis's `(v / 48) * 48 + 24`,
and the three that did **not** move were on that point already. So this is a
snap onto the 48-unit cell grid, not three steps — and the three archers say
so without a second capture.

**Only then the decompile, and it took one grep.** `set_new_location`'s
callers, and `Unit::fight@005fd4d0`'s first statement:

```
LAB_005fd648:
  set_new_location(this, div_3_table[x >> 4] * 0x30 + 0x18,
                         div_3_table[y >> 4] * 0x30 + 0x18, 1, 0)
```

`x >> 4` then `div_3_table` is `x / 48`; `0x30` and `0x18` are 48 and 24. The
gate above it turns on `recharging` (`UnitData +0xae`, settled by the type
record, not by the surrounding code) and on `param_5`, which all four call
sites pass as 0. `docs/ORDERS.md` §7.11 has the block whole.

The fix is that one call, in `do_attack` where the original has it — above
the reload gate, which is exactly the branch that skips it.

### What this did not establish

The gate's two widening arms are read, never diffed. A unit that is
`recharging` still snaps if it holds §7.10's re-entry latch on an invalid
target, or if its type is a cavalry archer (`unit_flags & 0x400`); nothing on
disk has a recharging unit enter `fight`, so `crates/sim` models the
`recharging == 0` row alone and the other two are named as seams in §7.11.

Nor is it established what the snap is **for**. Every 48-grid search
downstream starts from a cell, which is the obvious reading, but no run was
made to fail by starting one off-centre.

Parked **333** is untouched: `1/28`'s path stack is still 41 entries where
run19's block 8187 says 42. It is a different unit, a different frame and a
different function, and the widening did not name it.
