# Item 4019 — the first decoder

Opus 5.5 at `--effort medium`, lane B, base `42ca310d3`. One session. The second `render` item.

## What was booked, and what it turned out to be

The booking asked for four things:

- the piece → `<UNIT>` → `.bh3`/`.bha` resolution, extending `rondata::artdata`;
- the `.BH3` container decoded to vertices, faces, nodes and bounds, self-checking;
- the rest of the `.BHa` key fields;
- each format claim in `docs/FORMATS.md` with its evidence.

The score is pieces decoding, counted. Three things in the reading changed the shape.

- **`rondata` depends on `sim`**, so a decoder there would bring `sim` along to any client that used it. The decoders are
  in `render` (`chunk.rs`, `bh3.rs`, `bha.rs`), they decode from bytes, and they depend on nothing. `rondata` gains
  `render` as a path dependency for the resolution and the survey. That is not a cycle, and `render` still has no
  dependency. RENDERER §3.1's "decoders in `rondata`" is amended in place.
- **The header's last field is `num_chunks`, not `version`**, by the PDB's `ChunkHeader`. In every one of the 3,909
  files it is the count of the container's direct children. That turned the chunk walk into a self-check. FORMATS'
  `.BHa` paragraph is corrected in place, and so is its "object (id 8)", which is the root node's wrapper.
- **ptasev's converter was not opened.** The loaders (`BH3Method::load_bh3`, `load_vertex_data`, `load_verts`,
  `load_faces`, `load_texs`, `load_hier`; `AnimMgr::force_load`, `AnimObj::load_hier`) and the size arithmetic left
  nothing unexplained except the fields FORMATS lists as not established.

## Before any reading

- **Grepping for an existing build.** The integration branch had no `.BH3` reader. `docs/AI.md` and the journals name
  none. `artdata::key_times` reads the `.BHa` root's durations only.
- **No capture or packet was booked.** The disk had the whole answer: the install's 3,909 files, walked strictly.

## The reading, then the build

A Python probe over the install, a reading aid kept in the job directory and never committed, walked each file
against the loaders' layout before any Rust was written. Every `.bh3` passed the structural walk. Two findings shaped
the decoder:

- **The normals are not data the game reads.** `BH3Method::load_vertex_data` returns an error for id 3, and only
  `BH3LightMethod` copies them. 749 models carry `0xffffffff` words there. The first Rust survey failed 160 pieces on
  `NotFinite` for that reason alone. The normals are now kept as stored and unchecked, and the vertices, texcoords and
  transforms are still held finite.
- **Three `.bha` carry an `id 10` chunk**, and the first probe refused it. `force_load` closes it unread, so the
  reader accepts it (`n × 24` bytes) and records its count.

## The value diff

No sim word moved, and no floor was touched. The decoder's one claim with an original-side oracle is the `.BHa` root
times. `render::bha`'s first root gives the same `u16` times as `artdata::key_times`, which is diff-backed against
every dumped `end_time`, on all 2,062 files (`the_whole_animation_reader_agrees_with_key_times`). For one example,
the sheep `sheep_idle3.BHa`: 48 root keys, and both readers end on the same last time, whose frames are the 109 that
`the_install_s_gaia_lengths_match_the_dump_s` already asserts against run12's dump.
