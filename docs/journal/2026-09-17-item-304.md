## 2026-09-17 — item 304: the Great Lakes cost was `kill_current_path`, not the formation (Opus 5)

The item was booked off `docs/PATHFINDER.md` §18.3: with the suspend wired
(`worktree-loop-301-suspend`, `4521ccc`) East Indies goes 7812 → 8193 and
Great Lakes falls 7679 → 6862, and the fall was read as "run76's `1/28` ends
its formation early — it is already on a plain `ATTACK_TO` before 6858, so no
order change is left to free the stash."

**The formation is not early.** The brief's first instruction was to grep
run76's `GROUPS` record over 6850-6862 and widen it. run76 has no `GROUPS`
record at all — `DEATHS` was on, and the pool comes out empty — so the
widening had to be the whole `UNITDATA` block instead, every field and every
nested order record, frame by frame. Doing that took twenty minutes and cost
the hypothesis:

- The **original**, out of the dump: `GROUPATTACKTOORDER` on block 6860,
  `ATTACKTOORDER` on 6861. On that same frame `collide_frame` −1 → 6860,
  `collide` 0 → 1 against `collide_o 13`, the path stack empties, and
  `start_dist` 0 → **7680**. So the ungroup and the suspend are the *same*
  event: `resolve_unit_collision` step 6 runs a search, it suspends,
  `move_step` answers 0, and `do_group_move` degrades the squad
  (`docs/ORDERS.md` §8.3, item 236).
- **This crate, wired**: `run76_s_window_is_the_ai_squad_s_march` reports
  **zero** scoring kind or `GROUPORDER` rows over all 630 marching
  unit-frames. The squad holds its `GROUP_ATTACK_TO` to 6860 and degrades on
  6860, on the original's own frame.

What it *does* report is three rows on 6862 and 6863, `1/28` alone: order
flags 4 against 5, `dest` 0 against 1, path length 0 against 10 and then 13.
The original re-plans the frame after the ungroup and this crate does not —
because its `1/28` still holds the suspended search, and `do_move`'s §4.4
step 2 returns before every arm while one is pending. It stands there for the
rest of the capture.

**The missing line is one call.** `Unit::kill_current_path@005e31d0` pops the
stack back through the current segment's final waypoint *and* calls
`clear_partial_path`, with the call inside its own `0 < length` guard. This
crate had the pop and not the clear. `Unit::ungroup_move_order@005fd140` calls
it on every member that is not the leader, so in the original the frame a
formation degrades is the frame each follower's stash goes. That is the
"the order change frees the search" §18.3 named without naming the function —
and it is not an order-adder at all: the replacement `ATTACK_TO` is built by
`MoveOrder::operator=` and spliced into the list, no `add_*_order` runs.

Four functions call `kill_current_path` in the executable and this crate calls
it from the same four, so one line covers all of them.

**The value diff beside the word.** On 6862 and 6863, `1/28`: `dest` 0 → 1,

**What has teeth.** `killing_the_current_path_frees_a_suspended_search` in
`crates/sim/src/path.rs`, made to fail both ways: drop the
`clear_partial_path` call and the first assertion fails; drop the emptiness
guard and the second does. The guard is the whole difference between this
function and `kill_current_order@005e2cb0`, which clears unconditionally.

**What this did not establish.** Whether any other caller of
`clear_partial_path` is missing here. The executable has 63; only the
`kill_current_path` one was checked against a capture. The `Group::action_*`
family and the `think_carry*` family are the two blocks with no counterpart
call in this crate at all, and no run on disk reaches either with a stash
pending.

carry. Widening every dumped record on the frames either side, rather than

reading: the reading that followed was one function, opened because the dump
