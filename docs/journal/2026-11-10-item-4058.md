## The hypothesis about borrowed bytes, by value

The driver's guess was that the rules section and the header's run state are constant for one install and one
rule set. By value across the fifty (`what_our_file_borrows_is_constant_for_one_lobby_s_options`): the run-state
stretch, the semaphore and start frame 0 are one value everywhere, the 2017 sample included. The rules section has
**two values**: the three `STARTING_TECHNOLOGY` 3 recordings part from the other 47 in 274 single bytes, all in
Types, each 2 lower. The 47 include the sample, which has another map, difficulty and build. So the guess holds
**per option set**, and `from_lobby` only accepts a donor whose version and 30 option bytes match.

## Our file, and the twin

`recgame::from_lobby` computes the header from the `GAMEINFO` block and borrows the markers, the run state, the
semaphore and the rules from the donor (§8.2's table). Against the twin, the header **parts on two fields**:

- slot 1: `tribe` 11 (ours, the block's resolved nation) against 24 (theirs, "random", rolled after the header);
- `graphic_tick`: 0 against 2,801,115.

Everything else is equal: the inactive slots, the knobs, the blob and the rules. The packages are ours: frame 0's
`leader_options` (borrowed, identical on all 49) and one empty package on frame 24,000. Seen red: names written
`Player <play + 2>` adds both slots to the list.
