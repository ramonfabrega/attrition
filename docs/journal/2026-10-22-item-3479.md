## What the draft predicted, and what the bytes say

- **`bindkey.py` does not refuse a `dependent="0"` entry.** It never reads the shipped entry's `dependent`: it checks
  that the action is listed and writes its own `dependent="-1"` element (`--bindkey` through
  `unattended_capture.py`, 3442). F12 (123) is bound to nothing else in `data/playerprofile.xml`. The take's `I_KEY`
  record reads action **0x1e** for VK 123, so 0x1e is SYSTEM_TOGGLE_PARAM_CONSOLE by measurement, not only by name.
- **The window is modal.** `ParamRegisterWindow::exec@00934c30` calls slot +0x3c0, `Window::set_modal@00a55460`,
  with flags 0, and then hides. With flags 0 the call runs a nested loop, and `System::modal_idle@005994a0` calls
  `ParamRegisterWindow::process` and `Game::loop` from it. So no frame-keyed line reaches the open window. Every
  input is an `@after` line queued *before* `602 @key 123`, because the key line returns only when the window
  closes. recon3479-1 showed this: its `I_KEY` record for F12 lands after the fifth line's Escape.
- **Return needs no click in an edit box.** `Window::key_down_event@00a50920` passes an unhandled key to the
  parent. `EditBox`, `ComboBox` and `Scroll` leave slot +0x11c at `Window::on_key_down`, which forwards it too.
  `ParamRegisterWindow::on_key_down@00934360` takes 0xd from any child. No `@char` is needed: the window acts on
  the key-down, unlike 3445's popup.
- **Every registration leaves `cur_cat = cur_obj = 0`** (`registration@00935360` → `on_change_cat`). So the window
  opens on category 0, Lights/Sun. The draft's guard (`cur_cat != -1`, `cur_obj != -1`) always passes.
- **The draft's "Storm, Nuke, CircleRender are in no trace" was wrong for two of them.** run1094 already enters
  `Nuke::registration` (from `Game::init`, which calls `NukeOut::setup_parameter_win_data` and files `nuke_effect`
  under "Nuke") and `CircleRender::registration` (`circle_gen`, filed under "Misc Effects" beside the text bubbles)
  on frame −1. Neither the `nuke` nor the `ranges 1` line is needed. The category names are `internal_strings.xml`'s
  rows 0x2788, 0xd8cc and 0x1324 ("Splines", BorderSpline's), read with `console.py`'s `strings`.
- **What the draft could not see: the controls are built once.** `process@00934c90` builds the edit boxes and scrolls
  only while the control array is empty (`jne` at 0x934cd2; the clearing loop after it is dead). Nothing empties the
  array but `close@00934a50`, at teardown. So the controls stay Sun's twelve Scrolls for the whole game.
  `on_change_edit_box` gives control *i* to `EditBox::get_text` for every unconstrained parameter. Those are the
  plain-int overload `register_variable@00a39f90`, whose `constrained` field is 0. The other overloads (byte, float,
  dword) and `register_enum` are constrained. The call targets in each registration, read off the listing:
  - BorderSpline: ten calls to `a39f90`;
  - CircleRender: three calls to `a39f90`;
  - Nuke: one enum, then `a3a1e0`/`a3a110` only.

  So only Nuke's Return is safe. recon3479-3 took the Splines Return anyway, and it faulted in `String::String` under
  `get_text`.

## The twin and the cursor

Every input is shared, so there is no `--from`. `rngcmp.py`: **641 in common, 0 differing, 641 identical**.
`samegame.py`: **41 in common (1..639), 0 differ**. No record differs. The item expected the edit box's write, but
neither Return writes one: Sun's parameters are Scrolls and Nuke's are Scrolls and a combo, and `on_change_edit_box`
writes only the values of edit boxes. The two gamelogs differ only in four header lines (load timings, memory, CPU
speed).

The cursor pin (`--cursor 1400,1000`, `I_PIN` c = 0x578, d = 0x3e8) and the clicks: `click.h` drives the click
through the original handlers, and a click leaves the pinned point where it clicked, as a hand does. Both runs send
the same two clicks at the same points, so the pin moves the same way in each, and nothing parts. This is the
third clean `cursor=X,Y` take against its twin (Loop 3432), and the first that clicks.
