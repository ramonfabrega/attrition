## 2026-09-18 — item 348: the market's ability is Coinage, not a Market (Opus 5)

The brief said 8582 had nothing named on it and that I should not invent a
hypothesis. The widening took one command and named it.

### The extra draw was an address the trace's own table did not carry

`RON_DEBUG_SITES=8570-8595` on the run53 test: twenty-six frames, twenty-four
of them identical, and 8582 reading

```
frame 8582: ours 7 theirs 8 — at 0, ours Leader::make_stuff+0x221 theirs 6c93ad
```

`6c93ad` is a bare hex address because `SITES` had no entry for it. The
export's index puts it in `Leader::use_market@006c91c0`, at `+0x1ed`, and
that function has exactly one `Random::get(GameAccess::game_random, 0,
0xffff)` in it. Everything else on the frame — three `make_stuff+0x221`, two
`+0x63d`, two `Farms::inc_time` — is the same on both sides, in the same
order, one place down.

`make_stuff` calls `use_market(this)` before it does anything else, which is
why the extra draw sits at index 0.

`docs/AI.md` §32 had narrowed the market with this: *no draw in run53's whole

Thirty-four frames, the first on the word itself, then a 200-frame cadence

### The gate is a library tech, and this crate read it off a building

`use_market`'s gate is `(has_tribe_bonus(4) || has_preq(BUY_SELL)) &&
has_market && !get_nuke_embargo`. `BUY_SELL` is `TypeIndex` **685**;
`BASE_BONUSTYPES` is 684, so it is the second entry of `rules.xml`'s
`<TECHBONUSES>` — "Can buy and sell resources at the Market" — and
`has_preq`'s generic arm asks `has_tech` of that type's own prerequisites. It
has one: `<PREQ preq0="Coinage"/>`.

The **Market building's** `PREQ0` is *Barter*. Barter is Commerce 1 and
Coinage is Commerce 2, so the standing seam — *"owning an active market is
taken to imply it, which is true of the shipped tree (the Market's own
prerequisite is the tech)"* — was wrong by a whole library tech. This crate's
gate opened on Great Lakes **6383**; the original's opens where
`epoch[Commerce]` reaches 2, which a one-line instrumentation of `use_market`
put between 8382 and 8582.

The instrumentation is also what proves the gate is the cause rather than the
arithmetic: this crate's own shortfall vector already met the sell branch's
condition on **8185** (`need [0, 0, 32, 0, 0, 0]`, `bucket[wealth]` 11) and
**8382** (the same need, 27), and the original drew on neither. Two refusals
below the word with the right `need` and the right `bucket`, and only the
tech between them.

### The draw is price-free exactly where Great Lakes needs it

`docs/ECONOMY.md` has no market, which is why this crate took no draw at all:
which branch a short good takes is `calc_market_prices`. Except for wealth —

```c
if ((TVar3 == WEALTH) ||
   (calc_market_prices(this, TVar3, &price, &need6),
    (int)(bucket[WEALTH] - price) < need[WEALTH]))
```

— and `||` short-circuits. Wealth cannot be bought with wealth.

The rotation the draw seeds is price-free too, and so is the thing that
decides whether a *second* draw follows: the once-flag is cleared by a
candidate **passing** the stock filter, not by the sale going through
(`local_c = 0; uVar5 = 0` sits after the inner gate's `if`, not inside it).
So "nothing here is sellable" is decidable without a price, and that is
exactly the one-draw case. Both of Great Lakes' first two are it —

| frame | `need` | `bucket` | the three candidates |
|---|---|---|---|
| 8582 | `[0, 0, 64, 0, 0, 0]` | `[58, 55, 43, 68, 54, 0]` | food 58, timber 55, metal 54; none clears `need ≤ stock − 100` |
| 8585 | `[0, 0, 34, 0, 0, 0]` | `[14, 56, 12, 68, 54, 0]` | the same three, the same refusal |

— and the trace agrees on the count for both.

`sim::ai_make::use_market` is nine lines longer than it was.

### What this does not establish

- **`has_market` is still the approximation.** `LeaderData::has_market@
  006d5410` is `num_buildings[0x16] != 0` **and** a city of mine with
  `city_flags & 0x800`; this crate reads "an active market building of
  mine". run97 refuses to separate them — who 1's first city carries `0x800`
  on all 1,320 blocks of the window, unchanged — so no capture on this disk
  can falsify the substitution. The one that would: a game where a market is
  built outside every city's radius, with `CITIES` detail, checking
  `city_flags` for `0x800` on the frame it completes.
- **`get_nuke_embargo`** is still taken as zero, and nothing in a 24,000-frame
  Classical-to-Medieval game could say otherwise.
- **The buy branch takes no draw here.** A short good that is not wealth is
  skipped entirely, because its branch is a price. The original takes no draw
  in the buy branch either, so nothing is *lost* on a frame that buys — but
  nothing says this crate reaches the same branch, and a bucket that drifts
  would show up only as a missing sell draw later.
- **A sale's proceeds.** A wealth shortfall that *does* find a sellable good
  stops after one draw where the original sells and goes round again. run53's
  9182 (three draws) and 10182 (four) are where that must show, and both are
  past the word. The capture that would refuse the model: any frame at
  `LEADERS=9` on this map above 9182, whose `bucket` says whether the extra
  draws are second passes over wealth or first passes over other goods.
- **`BUY_SELL_COMMERCE_LEVEL` is a pinned constant, not a loaded one.**
  `rondata` does not parse `rules.xml`'s `<TECHBONUSES>`, so the bonus type's
  prerequisite is written into `crates/sim` with its citation rather than
  re-derived from the user's install. A mod that repoints it would not be
  noticed.
