## The integer form, and the sweep

`sim::pivot` holds the node's point in hundredths (`py` 2464), the scale
as 48/10 and a whole-degree sine at 2³⁰. The vector is `v0 = s(px cos d +
py sin d)`, `v1 = s(px sin d − py cos d)`, truncated toward zero. The
convention was fitted on two nodes (the pivot, and piece 145's release
node 0 with `px` 2.25) over 361 degrees each, to within 2.6·10⁻⁵.

The float oracle is the original's `get_position`, called under unicorn on
the packet for `d = 0..=360`. It is not the native twin. `lift.py` refuses
both functions on packed SSE (`set_all_pivots` at `005d8dcb`,
`cvtdq2ps`, and `get_position` at `0090b818`, `unpcklps`), the limit
`docs/EMULATOR.md` §8 names. Unicorn runs them unchanged, and on a
packet there is no singleton to synthesize. It agrees with the integer form on **all 361 degrees**. The
float's largest error from exact is 4.0·10⁻⁵. The nearest exact value to
an integer is 0.0161 away (25°, 65° and so on, 49.9839). That is a 400×
margin, so the two cannot disagree on this node at any whole degree.
Moving `py` by one hundredth fails the sweep at 40°. The table lives
outside git, and the test reads `$RON_PIVOT_TABLE` and skips without it.
