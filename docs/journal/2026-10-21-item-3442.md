## The reading, and the shape it supports

I read the keyboard path before writing anything: the export, `d3dgl.dll`'s listing, and the PDB's `KeyMapType` and
`keymap_options`.

- `d3dgl`'s window procedure calls `OnKey(vk, 1)` on a down and `OnKey(vk, 0)` on an up, after folding the numpad's
  digits. `WM_CHAR` calls `OnChar(ch)`.
- `OnKey` reads shift, ctrl and alt itself through the executable's own `GetKeyState`. Nothing on the keyboard path
  polls the OS keyboard except that and `GetAsyncKeyState` behind `ron::GetKeyStateAsync`.

So `@key` is `click.h`'s shape with nothing to pin: it calls the shipped slot, down then up, at the top of the line's
frame. There is no cursor-like polled state to pin, so nothing is installed. Before the press it calls `KeyMap::lookup`
(read-only, `on_key_down`'s own call) and records which action the key reaches. That record read take 1's failure in a
minute. `@char` exists for a letter's `WM_CHAR`. No line here sends one, which is why `OnChar` is not entered.

**The key-state hook (3444's question).** Yes: it is the same small step. Every modifier read is the executable's own
`GetKeyState` import, so one IAT slot answering a pinned high byte for a line's frame gives shift, ctrl and alt to
`OnKey`, `Options::exec`, `do_formation` and `do_rotate`. And to the minimap's `on_right_up`, if its reads are the
same import (not checked here). It is not built, because `@key` did not need it (parked 3442a).

**How the binding reaches the lane's profile.** `unattended_capture.py --bindkey ACTION=VK` (repeatable) writes
`bindkey.py`'s element into the lane's own `PlayerProfile/Player.dat`, replacing its empty `<KEYS/>`. That is the same
file and the same staged backup as `set_map`, `mute` and `set_lobby`, so the restore takes it out (the receipt's
five restored files). The template at `~/ron-capture-lanes/template` was read, never edited. Its `<KEYS/>` is empty,
and `bind_keys` refuses anything else.
