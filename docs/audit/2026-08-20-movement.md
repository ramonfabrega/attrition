A = `docs/MOVEMENT.md` + `crates/sim/src/movement.rs` (+ `lib.rs:process_movement`).

Verdict key: **A** = A right, **B** = B right, **both wrong**, **ambiguous**.

## 1. Disagreements (behaviour-changing)

### D1. Which position `Guy::move` moves, and what moves the unit's position — **B**

- **A:** "`Guy::move` is the integration, per figure"; the pseudocode walks *the
  unit* from `position` to `destination`. `lib.rs:815` applies `movement::advance`
  to `unit.pos` (the unit's authoritative position).
- **B:** Two positions. `Unit::x_internal/y_internal` (XOR `0x63637`) is the sim
  position, advanced by `Unit::move_step` once per frame from
  `Unit::work → do_job → do_move`. `Guy::x/y` is the body, which `Guy::move`
  walks toward `GuyData::des_x/des_y`, and `des_x/des_y` is set from the unit's
  position by `Unit::set_new_location`.
- **Evidence:**
  - `Unit/move_step@005faf30.c`: `uVar14 = *(uint*)&this->field_0x10 ^ 0x63637;
    local_40 = *(uint*)&this->field_0x14 ^ 0x63637;` … `set_new_location(this,
    CVar15, CVar13, 0, 0)` — moves the unit's own XOR'd position, bounds-checked
    against `GameAccess::world->field_0x18 * 0xc0`.
  - `Unit/set_new_location@005f8d20.c:158-160`:
    `pGVar1->field_0x5c = this->field_0x10 ^ 0x63637; pGVar1->field_0x60 = this->field_0x14 ^ 0x63637;`
    — guy `des_x/des_y` (`types.txt` GuyData +0x5c/+0x60) := unit position.
  - `Guy/move@005d9240.c`: `uVar12 = des_x - x; uVar10 = des_y - y;` … the
    step is applied to `field_0xc/0x10` (GuyData `x`/`y`).
  - `Unit/do_move@005f7b30.c:752`: `move_step(this, pMVar3, (int)param_1)`;
    `Unit/process@00610bc0.c:538`: `(**(code **)(*(int *)this + 0x188))()` and
    `vtables.txt:27770`: `+0x188 Unit::work`.
- **Verdict: B.** A implemented the body's kinematics as if they were the
  unit's. Every consequence below (D2, D3, D8) follows from this.

### D2. The 11/8 step multiplier — **B** (A right for the body, wrong for the unit)

- **A:** "The step is `speed × 11/8` … every quoted speed in the game's data is
  therefore 27% slower than what a unit actually covers." `step_distance()`
  applied to `unit.pos`.
- **B:** The unit's step is `get_speed(x,y,0)` (× `ai_speed` if > 1, × 5/4 for
  modern infantry); the **body's** step is `floor(GuyData::get_speed() * 11/8)`.
- **Evidence:** `Unit/do_move@005f7b30.c:557-566`:
  `param_1 = (*vtable+0x17c)(x, y, 0); if (1 < *ai_speed) param_1 *= ai_speed;
  if (is_modern_infantry) param_1 = (param_1*5 + sign&3) >> 2;` then
  `move_step(this, order, param_1)`. No 11/8 anywhere on that path.
  `Guy/move@005d9240.c`: `local_c = (iVar9*0xb + sign&7) >> 3` after
  `GuyData::get_speed` — asm `0x5d95ec imul eax,eax,0xb … sar ecx,3`.
- **Verdict: B.** A Citizen's MOVES 25 means the unit covers 25 units/frame
  (≈1.95 tiles/s), not 34. The body overtakes at 34 but is clamped to the
  sim point. A's "27% slower" conclusion is wrong.

### D3. Which angle the trig components use — **B**

- **A:** `sx = sinx(angle, step)` where `angle = find_angle(...)`; `movement.rs`
  `advance()` passes `heading` (the find_angle result) to `sin_component`.
- **B:** `Guy::move` uses the **body's facing after this frame's turn**
  (`guy.angle`), not `want`; `Unit::move_step` likewise uses `new` (the
  post-turn angle, `local_8`).
- **Evidence:** asm `0x5d963c mov ebx, [ebx+0x18]` (GuyData +0x18 = `angle`,
  written by `do_turn` inside `turn_towards`), `0x5d9641 mov ecx, ebx; call
  0x92d100 (sinx)`, `0x5d964b mov ecx, ebx; call 0x92d0c0 (cosx)`.
  `Unit/move_step@005faf30.c`: `if ((int)local_8 < 0) local_1c = -param_2;
  sin_table(...)`, `if ((int)local_8 + 0x40000000 < 0) ...` — `local_8` is
  `new` (= `cur ± ts` or `want`).
- **Verdict: B.** A's `advance()` moves along `heading` when `owed > 0`; the
  original moves along the partially-turned facing. Differs whenever
  `0 < owed <= 2*rate`.

### D4. `UNIT_TURN_SPEED` in memory and the scale of the type's turn speed — **B**

- **A:** "`UNIT_TURN_SPEED` is written `1/1 rate` … used as plain integer
  multipliers — 1 and 2"; `Tuning::RON.unit_turn_speed = 1`
  (`tuning.rs:377`); type value's scale "not established", "`>> 8` suggests 8.8".
- **B:** `UNIT_TURN_SPEED = get_fraction(…, 0x100) = 256`; type turn speed =
  `degrees_to_angle(TURN_SPEED)`, a 2^32-circle angle; so
  `(ts >> 8) * 256` is `ts` with the low 8 bits cleared.
- **Evidence:** `Constants/init@00569a90.c:77-78`:
  `iVar4 = get_fraction(this_00, …+0x91f0, 0x100); this_00->unit_turn_speed = iVar4;`
  and `String/fraction@00a1d110.c`: `return (iVar2 * param_1) / iVar4;` →
  `1*256/1 = 256`. (Contrast `unit_move_speed` at `:75-76` uses `0xc0` →
  `1*192/192 = 1`, which A got right.)
  `UnitType/init@0061ab50.c:502-505`: `get_text_num(…+0x22b14 …);
  iVar13 = degrees_to_angle(unaff_EDI); field_0x2c4 = iVar13;` — asm
  `0x61b43f call 0xa25620 (get_text_num); 0x61b444 mov ecx,eax; 0x61b446 call
  0xa28eb0 (degrees_to_angle)`: the TURN_SPEED number is the argument.
  `_global/degrees_to_angle@00a28eb0.c`: `… + iVar2 * 0xb60b60 + (d/90)*2*0x20000000 …`
  (1° = 0xb60b60).
- **Verdict: B.** `Tuning.unit_turn_speed` must be 256 and the type input is a
  binary angle from degrees. A's open question is closed. (A's statement that
  "nothing in this document depends on the answer" is itself wrong once D5 is
  taken into account: the 1°/frame floor is `unit_turn_speed * 0xb60b`.)

### D5. What `GuyData::turn_speed` returns — **B** (A incomplete in a behaviour-changing way)

- **A:** `turn_speed = (type.turn_speed >> 8) * UNIT_TURN_SPEED`, ×2 if packed.
  `advance()` takes a constant `turn_rate`.
- **B:** After that base: decorative guys get 0x40000000; **if `last_speed == 0`
  and `guy_flags & 0x10`: return 0x80000000 (instant)**; mode 1 returns base;
  mode 0 (used by `move_step`) returns
  `max(UNIT_TURN_SPEED*0xb60b, base / (floor(avg_speed/4)+1))`.
- **Evidence:** `GuyData/turn_speed@005de340.c`:
  `if ((this->last_speed == 0) && ((this->guy_flags & 0x10) != 0)) return -0x80000000;
  if (param_1 != 0) return uVar3;
  uVar2 = constantsc->unit_turn_speed * 0xb60b;
  uVar3 = uVar3 / (((avg_speed + sign&3) >> 2) + 1U); if (uVar2 < uVar3) uVar2 = uVar3; return uVar2;`
  `guy_flags & 0x10` set in `Guy/init_real@005db6b0.c:184-212` for non-packed
  types with objmask 'F'(0x20) or 'M'(0x1000) or unit_flags 0x10, and
  unit_flags&2 clear. In `Guy::turn_towards@005d9720.c`,
  `uVar2 = turn_speed(…,1); if (uVar2 < uVar4) {turn} else {snap}` — with
  `uVar2 = 0x80000000 >= any owed`, a stopped foot/mounted unit snaps to the
  target and `Guy::move`'s gate `(iVar9*2 = 0) < uVar7` is false, so it moves
  the same frame.
- **Verdict: B.** In the original, most land units turn instantly from a
  standstill; A's "heavy units feel sticky when reversed" and the test
  `a_unit_turns_before_it_walks` (14 frames stood still) describe behaviour the
  original only has for units without `guy_flags&0x10` or already moving.

### D6. `unit_masks & 0x10` halving = "being damaged" — **A wrong, B (unnamed) right**

- **A:** "for an ordinary unit type, **being damaged halves it**".
- **B:** bit 0x10 halves land speed; name not settled.
- **Evidence:** only setter `Unit/target_opportunity@005fffc0.c:129`:
  `unit_masks |= 0x10` inside `if (is_move(...)) … if (vector_dist(...) <= radius_sum)`
  (the unit is moving and a target object is within the two units' `+0x244`
  radii); only clearer `Unit/work@0060d180.c:449`: `field_0x68 &= 0xffffffef`
  at the end of every `work`. No health/hit-point test anywhere on that path.
- **Verdict: both wrong on naming, A wrong on semantics.** The bit means
  "moving in contact with a target this frame", not damaged.

### D7. The 0x800 tile halving needs `z <= 0` — **B**

- **A:** "standing on a world tile carrying flag 0x800 halves it again".
- **B:** "if z_internal <= 0 and tdata[tile] & 0x800: s /= 2".
- **Evidence:** `UnitData/get_speed@00608720.c`:
  `if (((int)(field_0xc ^ 0x63637) < 1) && ((worldc->field_0x138[tile] & 0x800) != 0)) iVar1 /= 2;`
- **Verdict: B.** A omits the z condition (flying/elevated units on the tile
  are not halved).

### D8. Group cap applies to the body? — **B**

- **A:** `group_capped()` is presented as part of the speed that feeds the step.
- **B:** the cap is gated on `flag == 0`; `GuyData::get_speed` calls with flag 1,
  so the **body** is never group-capped; only the sim point (`do_move` passes 0).
- **Evidence:** `UnitData/get_speed@00608720.c`:
  `if ((((param_3 == 0) && (-1 < this->group)) && (local_8 == 0)) && …)`;
  `GuyData/get_speed@005de410.c`: `(*vtable+0x17c)((this->x).value,(this->y).value,1)`;
  `Unit/do_move@005f7b30.c:558`: `(*vtable+0x17c)(x, y, 0)`.
- **Verdict: B.** Consistent with D1: the cap belongs to the unit step, which A
  does not have.

### D9. Transport/marine bonus scaled by "the player's age" — **both wrong**

- **A:** "transport and marine bonuses scaled by the player's age".
- **B:** `(leader.military_tech_count ^ 0x63187) * bonus`.
- **Evidence:** `Unit/update_speed@006055c0.c`:
  `(*(uint *)(*(int *)&leaders.list[who].field_0x6eb8 + 0xe8) ^ 0x63187)`;
  `types.txt:42383` `+0x6eb8 LeaderDataEncrypt* data_encrypted`;
  `LeaderDataEncrypt +0xe8 int[4] epoch` → `epoch[0]`.
- **Verdict: both wrong on the name; B closer.** It is `LeaderDataEncrypt::epoch[0]`
  (the first of the four library levels, i.e. the Military level), not the age.
  Only matters for `MILITARY_TRANSPORT_BONUS` (0) and `AMERICANS_MARINE_SPEED_BONUS` (2).

## 4. Doubly confirmed (A and B agree, and the decompilation says so)

- Position unit: 1/192 tile; `UNIT_MOVE_SPEED` = `get_fraction(…,0xc0)` = 1;
  MOVES is units/frame. `Constants/init:75-76`, `String/fraction`.
- `get_speed` floor 3; ×9/8 for order type 10, ×10/8 for 12 with
  `unit_masks&0x40000` else ×9/8; general 0x162 + vslot 0x10c ×2; group cap
  only with no action order and non-zero group speed. `UnitData/get_speed@00608720.c`.
- Angle = signed 32-bit binary angle, north 0, east 0x40000000, y south;
  `find_angle` polynomial `t = lo*0x4000/hi; (0x2800 - (|0x1333-t|*0xb00>>14))*t & ~0x3fff; *4`
  and the eight-way quadrant table (A's `match` == B's table ==
  `_global/find_angle@0092d130.c`). 45° → 541,917,184 (0x204d0000).
- Sine table: 256 entries, `(int)(sin(i*1.570796327/255.0)*65535.0)`, indexed
  `(a&0x3fffffff)>>22` with 22-bit fraction, `tbl[(i+1)&0xff]`, 32-bit wrapping
  interpolation multiply, three magnitude paths split at `< 0xffff` /
  `> 0xfffffe`. `_global/sin_table@00a46a00.c`.
- `sinx`/`cosx` fold: `mag==0 → 0; angle<0 → mag=-mag, angle&=0x7fffffff;
  angle&0x40000000 → 0x7fffffff-angle`; `cosx = sinx(angle+0x40000000)`. asm 0x92d0c0-0x92d129.
- `Guy::turn_towards`: `d = target-angle; d>0x80000000 → ~d`; snap below
  0x2222220 (3°) or when `ts >= d`; else `angle ± ts`, returns `d - ts`.
- `Guy::move` gate: `if (uint)(2*turn_speed(1)) < owed: return` (unsigned,
  wrapping); body step `floor(g*11/8)`; Manhattan snap `|dx|+|dy| <= step`;
  per-axis clamps `|sx|>|dx| → sx=dx`, `|sy|>|dy| → sy=-dy`; `y -= sy`;
  `x -= off_x, y -= off_y` before adding.
- Movement (both `work` and `Guy::process`) runs after healing, cloak,
  attrition and supply in `Unit::process`.
- `UNIT_PACK_TURN_BONUS` = 2 via `get_item`, applied when `unit_masks&0x80000`.

## 5. What must change

**`docs/MOVEMENT.md`**
1. Split the model: `Unit::move_step` moves the unit (D1), `Guy::move` moves the
   body toward it. The per-frame step section currently describes the body.
2. Remove the "27% slower" claim; the unit step is `get_speed` (× 5/4 modern
   infantry, × ai_speed) (D2). 11/8 is the body's catch-up rate.
3. The trig components use the post-turn facing (D3).
4. `UNIT_TURN_SPEED` = 256; TURN_SPEED is degrees → `degrees_to_angle`; close
   the "not established" paragraph (D4). Add `GuyData::turn_speed`'s instant
   (stopped + `guy_flags&0x10`) and moving-mode (`/ (avg/4+1)`, floor ≈1°)
   rules (D5).
5. `unit_masks&0x10` is "in contact with a target while moving", not damaged
   (D6); add `z <= 0` to the 0x800 halving (D7); the group cap is on the unit
   step only (D8); transport/marine scale is `epoch[0]`, not age (D9).
6. Move `move_step`'s turn-in-place/limit/half-step rules from "open" to
   established, per §2 above.

**`crates/sim/src/movement.rs` / `lib.rs`**
- `Tuning::RON.unit_turn_speed`: 1 → 256; `turn_speed()` input is a binary
  angle (`degrees_to_angle(TURN_SPEED)`), so add `degrees_to_angle`.
- `advance()`: use `facing` (post-turn), not `heading`, for `sin_component` /
  `cos_component`.
- `process_movement` applies the body rule to `unit.pos`. Either rename it as
  the body and add a `move_step`-shaped unit step (step = `get_speed`, no 11/8,
  move_step's turn limits, `manh < 2*step` clamp gate, tolerance arrival), or
  at minimum drop `step_distance()` from the unit's step.
- Tests `a_step_is_eleven_eighths_of_the_quoted_speed` (keep, but as the body
  rate), `a_unit_turns_before_it_walks` and `a_unit_walks_east…` (68 frames at
  34/frame) encode the wrong model and will need new expectations.
