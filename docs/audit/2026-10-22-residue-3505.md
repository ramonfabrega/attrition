# The read residue candidates, re-derived blind (item 3505, 2026-10-22, Opus 5.5)

Twenty-nine open rows of the blind list (`blind::NEVER` net of `blind::RESIDUE`) had been read as unreachable by two
drafting subagents of the fifty-first tranche: draft-items-52's rulings (`get_follow_order`, and the residue
candidates that follow it) and draft-items-53's `## Residue candidates`. Neither draft is in git. The reasons there
were written by the drafts' authors, and nobody had checked them.

## Method

1. **The list, blind.** A script took only the `Class::method@ADDR` tokens out of the two sections and intersected
   them with the open rows on the base. It found twenty-five rows. Four rows that draft 52 named without an address
   (`OrderList::get_new_data`, `get_data_type`, `Tribes::walk_data`, `Special::walk_data`) were looked up by name in
   the export's `INDEX.tsv` and sent as a second list. `Unit::kill_group_order` is item 3504's live route, not a
   candidate.
2. **The blind reader** was one Opus 5.5 subagent (`lean`). Its brief carried the names and addresses, the export,
   `rise_z.map`, the PE, the pinned traces' union and the rule that a slot is read on the receiver's most-derived
   vftable (Loop 3500). It was forbidden the drafts, `docs/` and `blind.rs`. It wrote a section per row,
   incrementally. Its tools were a PE reference scanner, a vftable slot reader and a decompile dispatch lister.
3. **Adjudication** was mine, against the drafts' reasons. Where the two readings agree that a row is unreachable,
   it becomes a `RESIDUE` row. Where they disagree on the verdict or on the evidence, I went back to the decompile
   or the `llvm-objdump` listing, below. A row that either reading calls reachable stays open.

## The adjudications

**(1) `is_sea_trade`.** The blind reader found the one unguarded object dispatch of Build's +0x28, which the drafts
did not name: `Group::action_trade`'s line 112 calls +0x28 on the destination when +0x24 (`is_trade`) answers 0.
The function's head (lines 52–69) has already required `is_trade` to answer non-zero, on the object that the
destination's +0xb0 returns. I read Build's and Wall's +0xb0 off the image: it is `0041c000` (`mov eax,ecx; ret`,
the folded `get_graphicwinxml`), so it returns `this`. Both reads are therefore of one receiver, and `is_trade` reads
only the type (`is(0x19e)`). The `QUEUE_FIRST` arm, the only code between the two reads that changes anything,
recurses before line 112. The +0x28 call cannot run. **Killer**: a destination whose type changes between the two
reads inside one call. None exists.

**(2) `ObjectTypeOut::draw`: the evidence disagrees, so the row stays open.** The blind reader's dispatch lister
matched `+ 0x140))(` on one line, and it missed `ObjectsOut::pop_all_zoomed_in`'s line 121, where
`(**(code **)(**(int **)(unittypes._16_4_ + iVar8 * 4) + 0x140))` breaks before its argument list. I re-scanned
every slot of the twenty-nine rows for that line-broken shape, filtered to type receivers. This is the only miss on
a type receiver. The other hit, `draw_cursor_follows:127`, is gated on `is_unit_type` and so lands on UnitType's
override. Line 121 runs for a falling building whose `falling_build_type` entry is not a build type. Its
`unittypes[i]` is then a non-unit type only if a non-build type is ever appended. The appender is inlined somewhere
the export does not name: `GraphicPieces::inc_time` only removes entries, and no named function writes them. Neither
reading established the predicate, so the row parks (3505a).

**(3) `is_flat`: the blind reader is right.** `Leader::produce_building`'s listing has `6e230d mov ecx,[eax+edi*4]`
on the `goodtypes` list (`0xc061ac`), then `6e2310 mov eax,[ecx]` and `6e2312 call [eax+0x94]`, with no guard.
GoodType's Type vftable holds `is_flat` at +0x94 (`0xb44c04`). The arm is the AI's site scoring for a building of
the `is(0x1bb)` class other than 0x1a2, after `World::gather_at`, on each good with a non-zero amount. Draft 53's
"all eleven type-receiver dispatches are on a build type" missed it. The row is reachable but unstaged (3505b).

**(4) `is_item_type`.** The blind reader names a live route: the Scenario Editor's resources page.
`Options::draw_cursor_follows:85` and `mouse_move:125` make unguarded type +0x20 calls on `types.list[cur_rare]`.
Draft 52 called that arm "no route", but an editor session is an input this project's click-free pool could stage.
Open (3505c).

**(5) `process_move_near`.** Both readings agree that no builder in the shipped game writes command type 8. The blind
reader adds that `CommandPackage::process` dispatches whatever type byte a recorded game or a network peer carries.
A hand-edited `.rec` played back is a capture this project could stage. Open (3505d).

## `get_follow_order`: a row, not a rule

The listing gives a four-byte body (`486c60 lea eax,[ecx-0x24]; 486c63 ret`). Its vtordisp thunk follows
immediately (`486c64 sub ecx,[ecx-4]; 486c67 jmp 0x486c60`). `rontrace.funcs.excluded.txt` excludes the entry as
"next entry under 5 bytes away", and both pinned traces enter the thunk (run321 on 620, run1032 on 708). The blind
reader found no other reference to `00486c60`. That makes the thunk's unconditional `jmp` the body's sole
predecessor, so the body ran.

A `blind` rule that credits an excluded entry with its sole unconditional predecessor would need its own scan, its
own test, and a pin of the excluded list against the image, all for one row: draft 52 found it the only open row
on the excluded list. The precedent is `ObjectData::is_in_range@0064e4a0`'s row, "entered, and no instrument sees
it". The smaller change is one `RESIDUE` row in that form, so that is what landed. If a second excluded row with a
thunk predecessor turns up, the rule earns its place then.

## Confidence and what is not established

- Each type-slot row is a decompile-level negative: no type receiver at that slot, after the line-broken re-scan.
  The residual risk is a receiver whose provenance the decompiler hides. The reader calibrated on `is_unit_type`'s
  slot +0xc, where it found about sixty unguarded type sites, entered in the union.
- `GroupMoveOrder::is_fleeing` rests on the existing `MoveOrder::is_fleeing` row's slot reading. The bytes are not
  scanned for a +0x28 order dispatch.
- Only `Special::walk_data` carries "no reference in the executable", which
  `every_unreferenced_row_is_unreferenced_in_the_image` re-checks against the install. Every other row has a vtable
  home and rests on the reading.
- No capture was run. Each row's falsifier is a trace that enters it, which fails `the_residue_is_on_the_blind_list`.
