1. **`WorldData::is_valid`: agrees.** The first reading (§20) must be
   re-derived in four steps. The reader re-derived the first by itself:
   the pair tests and the fall-through. Its addresses (`859a4b`..`859b1c`)
   sit inside §20's 0x859776..0x859b1e, and its rule (equal flanks
   that differ from C fire; none fired ⇒ the four calls) is §20's.
   - **The reader's UNSURE comes from a shape the code closes.** It named
     the cell that would get through: an `OCEAN` C whose four orthogonals
     equal it, with a land diagonal, so that no pair test fires. Such a
     cell is §19.2's (B), and `TerrainOut::check_for_tendrils@00859eb0`
     runs on it. When every orthogonal flag is 0 and a diagonal's flag
     is set, `check_for_tendrils` calls `set_edge_x`/`set_edge_y` with
     4 or 1 at shift 6 on **C's own** two flank edges (NW: 4 on W and N;
     NE: 4 on E, 1 on N; SW: 1 on W, 4 on S; SE: 1 on E and S). That
     is §19.3's account. `check_blocks` clears such an edge only when
     it is full (7) and C → F is 1. When F equals C,
     `is_combo_acceptable` returns 2 (same land, same sub), so the edge
     keeps its 4 or 1. The shift-6 word is then non-zero, and
     `create_transition_renderables` never calls the arm. The reader's
     model saw exactly this: every (b) cell non-zero "from shift-6
     tendril edges on shared edges". So the reader's keep and §20's are
     the same predicate. Only the attribution differs: the reader
     credited neighbours' writes, but C's own pass writes them.
   - **Steps two to four (C → F 1 on both flanks, `SANDY`'s one one-up
     land, distinct flanks ⇒ P1) were re-derived here**, not by the
     reader. `halfland::is_combo_acceptable` was compared with
     `TileSet::is_combo_acceptable@0087abe0` branch by branch, and they
     match. The reader listed a fourth one-up clause, which §19.1's
     prose omits: lower land, C's sub 0, and D's sub `num_tiles[d] − 1`.
     The crate already carries that clause (the `s2 == 0` arm), and on
     the three shipped lands it is never reached with result 1: every
     `l1 < l2` pair is `(0,1)`, `(0,2)` or `(1,2)`, and each is
     answered earlier. So §19.1's list of 1s is complete for shipped
     tilesets, and
     `halfland::tests::the_diagonal_arm_reaches_is_valid_only_past_a_p1_pair`,
     which enumerates the crate's function, pins steps three and four.
   - **The counts are independent and agree.** The reader's full-pass
     model gives 0 entries on 135 initial passes. That is §19.4's 0 P1
     and 0 P2 on the start grids, reached by a different scratch port.
     The reader did not search console plants. §20's `plant.py scan` (66
     entries, 0 reaching `is_valid`; 2,152 of 8,201,021 pairs, 0) stands
     unchallenged.
   - **The residual both readings name:** a P1 pair surviving
     `verify_land`'s depth leak (3863a). No grid or plant sequence on
     disk holds one.
2. **`MapScenario::make`: agrees. The route is corrected, and the verdict
   does not change.** The first reading (§18.1, the queue's text) says the
   function is "reached only by style 0x1a through `Setup::build_game`
   line 271, a scenario game".

     `param_2 == 0`, on `new_map(World::map)`. A scenario game takes the

   - `World::map` is never 26 from the lobby or the console.
   - Style 26 is minted by `ConquestGame::build_conquest_game` line 75,
     `(map_style == 8) * 2 + 0x18`, and dispatched at `797e7d`

   - So `MapScenario::make`'s producers are a custom-map Conquer the
     World and the editor's `generate_map`. Both are cut from v1, so

   - §18.1's "the one dispatcher of +0x64 on `game_map`" was true as
     written: `build_conquest_game` dispatches on a local, not on
     `game_map`. But it is not the whole set of +0x64 dispatchers that
