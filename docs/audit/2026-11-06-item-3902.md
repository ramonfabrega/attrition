## Part 2: adjudication

### Where the readings agree

- **The callers of the pair.** `report.py refs` (§388.3) and the reader's byte sweep agree, and the lane's own
  rel32 sweep agrees: `5e3310 ← 710b1e`, and `710aa0 ← 5e76c4, 5ff78f`.
- **`do_group_attack`'s site is dead**, as §382.1 has it (item 3887 agreed). The reader re-derived it from the
  order pool, with no maker of a type-20 order.
- **`repath` runs before the head test** on every path into `find_new_target` (§388.2; the reader, `5ff70d`).
- **The `+0x14` and `+0x2c` answers of every order class.** §388.2's table is the reader's set: move = {1, 2, 3, 4,
  18, 19, 21}, and group = {19, 20, 21, 22}.
- **The `do_move:105` entry (`5f7c66`) is closed.** Both readings have `get_action` returning `ATTACK` and `repath`
  stopping on it.

### Disagreement 1: `repath`'s type 18. The reader is right; the verdict does not change.

§388.2 has type 18 killed "when it lacks the action bit". The listing has `5e2a27 cmpl $0x12; 5e2a2a je 5e2ad6`
inside the first kill set. So type 18 is killed whatever its flags, and the decompile's later `== 0x12 && flags & 4`
re-test is unreachable. After `repath`, therefore, the head is never a `FormOrder`. §388.2's one "exception" does
not exist, and its conclusion only gets stronger.

### Disagreement 2: what `kill_group_move` removes. The reader is right, and §388.2's premise is wrong.

§388.2 says `Unit::kill_group_move@005e3400` "kills only move orders whose group view (`+0x94`) carries the id".
It walks every node from the tail (`head_node->prev`) and steps through `+4` (`prev`). On a match it calls
`kill_current_order(this, 0)`. That function re-seats `current` on the tail (`:154-158`) and removes and frees the
tail (`remove_current`, `give_obj`, `:160-171`), **whatever node matched**. `Unit::kill_group_order` has the same
shape. So a deeper match kills the current order.

§388.2's conclusion "so `repath` adds nothing to the list" still holds, since no order is added. But "the head
after `repath` is the `ATTACK`" holds only if no deeper node in the same list carries the same group-move id.

The lane read the id: `add_group_move_order:45-52` writes the `GroupOrder` subobject at `+0x50`, and its `id`
(`+0x5c`, `piVar3[0x17]`) is `param_4`. `Group::action_move_near:780` passes
`(group.id + frame*10)*100 + order_num` (`GroupData +0x4`, `+0x2c`). `order_num` grows by one per `action_move_near`,
`action_patrol` or `action_attack` call, and only `Group::clear` resets it.

`finish_insert` re-issues the orders it copies through `action_move_near` or `redo_patrol_order`, so it mints fresh
ids and never duplicates one. Within one group the id is strictly increasing between `clear`s.

The id is not unique across groups, though. For example, gid 1 with `order_num` c and gid 0 with c+100 on the same
frame give the same id. So route 2 needs all of these: one unit holding group moves from two groups (a regroup
with the old move kept queued), an id collision, and an `ATTACK` between the two. **The lane did not settle it.**
It is the weaker route.

### Disagreement 3: the callers of `find_new_target`. §388 read one of eight, and route 1 is open.

§388.2 closed "every entry from `do_move:105`" and §388.3 called the pair closed. The rel32 sweep gives eight
`E8` sites into `005ff6a0`, the reader's eight. The lane read route 1 to the function, and every step is a state
the game can hold:

1. **The first call.** `Unit::do_attack` calls `fight(…, param_5 = 0)` on a tail `ATTACK`. On a unit type with
   `+0x2b8 & 4` and `param_3 == 0`, `fight:1052` (`5fe113`) calls `find_new_target`. `repath` stops on the `ATTACK`,
   which answers 0 at `+0x2c`, and `kill_current_order` kills it. Now the tail is the `GROUP_ATTACK_TO` it had
   interrupted.
2. **`find_melee_target(this, -1, p, 0, 1, 0)` → `find_nearby_target`.** Here `param_4 = 0`, so `local_2c` is
   "activity is `GUARD`" (`:165-184`), and it is 0 for a unit on an attack-move. `:551-580` then reads the order
   type `GROUP_ATTACK_TO`, `Group::is_attacking_to`, and the unit type's `+0x10c` = 0, and calls
   `Group::action_attack(group, target, who, 0, QUEUE_FIRST, 4)` **instead of adding an `ATTACK`**. It returns the
   target, so `fight`'s `uVar28 ≥ 0`.
3. **`action_attack`'s `QUEUE_FIRST` arm (`:181-191`)** runs these steps:
   - `set_up_insert` copies the **leader's** flag-4 orders.
   - `action_halt` runs `close_orders` on every member that is neither a plane nor entering (`action_halt:79-85`).
     **This unit's list is now empty.**
   - `action_attack(…, QUEUE_NEW, 4)` runs.
   - `finish_insert` re-issues the copies at `QUEUE_LAST`.
4. **`QUEUE_NEW` may give this unit no `ATTACK`.** Its first arm (`:253-279`): if the target is an active building
   that `BuildData::check_capture_eligible` accepts, it calls `Build::check_capture` and
   `action_move_to(…, QUEUE_NEW, …)`, and **returns**. This unit gets a group move and nothing else.
5. **A `GROUP_PATROL` survives the insert.** `Unit::add_patrol_order:75` sets flag 4 on every patrol order,
   unconditionally. So a leader's queued `GROUP_PATROL` is copied by `set_up_insert` and re-issued by
   `finish_insert` through `redo_patrol_order` (case `0x16`).
6. **The second call.** `fight:1060-1061` (`5fe25f`) calls `find_new_target` again when `param_4 == 0` and either
   the stance-and-duty clause holds or `find_attack_pos` fails. `repath` kills the new `GROUP_MOVE` (through
   `Group::kill_group_move`) and any re-issued `GROUP_ATTACK_TO`. The head is the `GROUP_PATROL`, which answers 1
   at `+0x2c`. The unit is still grouped, so it calls **`Group::kill_group_order` at `5ff78f`**.

**Not read to the end:**
- `fight`'s second-call gate on a capture-eligible target.
- Whether `find_nearby_target` returns such a building to a melee searcher.
- Whether `is_attacking_to` holds on that frame.

One point weighs toward the route being dead in practice. Without a queued patrol, the same sequence leaves the
list empty at `5ff752`, and `piVar8` is null, so the original would crash there. Either the gate is shut more
often than this reading shows, or the combination is rare. A reading cannot tell those apart; a take can.

**The take that settles it is not 3900b's staging.** That staging tests `do_move:105`, and both readings agree it is

- **Setup:** a grouped melee line whose type has `+0x2b8 & 4` (and `+0x10c` = 0), given a group attack-move
  (`GROUP_ATTACK_TO`) and then a shift-queued patrol, so that the leader holds a `GROUP_PATROL`. It engages a
  defender beside an enemy building at capture HP.
- **Trace:** `cover=1`, on `005ff78f`, `00710aa0`, `00712490` and `005e3310`, with `UnitsSync` on the frames of
  the engagement.
- **The killer:** a `HIT` on `00712490` from `00648da0` on a frame where `00710aa0` is never entered, with
  `find_new_target` entered twice by the same unit, kills route 1 for that staging. A `HIT` on `00710aa0` moves
  both rows to entered.

`RESIDUE` candidates with no route" are struck and pointed here. §388.2's type-18 clause is corrected.
