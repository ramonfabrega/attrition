## Part 2: adjudication

**Rows 1, 2, 3, 5, 6, 7 and 8 agree** with §384 on verdict and on predicate.
The copy counts match §384's table: 15, 6+1, 1, 0 (two rel32), 14, 22, 12. The
`.text` counts match too: 0, 0, 0, 0, 6, 19, 0. The evidence differs in three
places, and none of them changes a verdict:
- **Row 2.** The reader rules the Wall copies out through the Build-cast
  receivers. §384.2 rules them out through Build's overrides and "no live Wall"
  (§383.2). Both readings rest on no live object being a Wall, which item 3887
  ratified, and each excludes the slot independently.
- **Row 7.** The reader lists six of §384.7's eight table-identity sites. It
  omits `Console::find_good`'s Good guard and counts `Build::process`'s three
  together. The fallback is dead on the same premise either way: Build, Good
  and Item have no subclass.
- **Row 8.** The reader proves the `unittypes[i]` receiver is a UnitType from
  the constructor's last table store. §384.8 goes further and names the
  appender, `emit_destroy_particle`, and the types its two callers pass. Both
  land on the same predicate.

**Row 4 disagrees. Settled for §384.4: UNREACHED.** The reader's chain from
`check_all` to an order's `+0x8` is correct, but it holds only if an order of
type 25 is still in a unit's list when the turn ends. The reader did not check
that, and the decompile says it never is.

- `Unit::come_out@00617c10` calls `add_spec_anim_order(this, 1, …)` (mode 1)
  at line 1525. At line 1544 it calls `do_spec_anim(this, update_order(this))`
  on the same order. `Unit::do_spec_anim@005e5880` returns early only when the
  mode is 2. Otherwise it sets the counter (`pUVar3[1].flags`) to 1 before
  comparing it with `iVar7`, which is 0 or 1. So the compare always passes, and
  in mode 1 both arms end in `kill_current_order(this, 0)`. The order dies in
  the call that made it.
- `Unit::land_plane@005e9950` calls `add_spec_anim_order(this, 0, …)` (mode 0).
  Its last act is a call through Unit's vslot `+0x188`, which is `Unit::work`
  (`vtables.txt`, `Unit::vftable@00b417d0`). `Unit::work@0060d180` can return
  before its `do_job` (line 417) in the following cases, and none of them
  applies to a fresh SPECIAL_ANIM order:
  - a null order, or one without flag 4 (`add_spec_anim_order` sets `flags |= 4`);
  - the caravan arm, which a plane is not in;
  - the MOVE_TO and slot `+0x18` arms.

  `do_job` dispatches SPECIAL_ANIM to `do_spec_anim` (line 78). In mode 0 the
  counter is also 1 and `iVar7` is 0, so the mode-0 arm runs. It ends in
  `go_inside` then `kill_current_order`, or `kill_current_order` then `die`.
  Either way the order dies inside `land_plane`'s own call.
- These are the only two adders. The reader found the same two, and
  `SpecialAnimOrder::SpecialAnimOrder@00484f10`'s one caller is
  `get_new_order` for type 25. So when `check_all` walks, no list holds one, a
  save writes none, and a load reads none.

The traces agree. A trained unit with a graphic piece comes out through `come_out`'s mode-1 arm
on a frame past 0, and run223 (GOLDEN chapter seventeen) enters `land_plane`.
None of the 144 pinned traces enters `004849a0`. The reader's own falsifier, "a
lobby trace past the first trained unit that never enters `004849a0`", is
therefore already on disk 144 times. Its REACHED is refuted by the decompile
and by every trace.

**Verdicts: all eight `RESIDUE`.** One killer is unchanged and shared by all
eight: a `cover=1` trace that enters the row's address. Row 4 has a second: a
`UnitsSync` dump that prints an order of type 25. Row 5 has one too: a rules
row carrying `l`, which would be a mod.

## For the method

The reader's one wrong answer came from proving that a walk reaches a slot
without asking whether the object lives long enough to be walked. A brief
for an order or list row should ask for the producer's lifetime as well as the
dispatcher.
