## Disagreements (behaviour-changing)

### 1. Do supply wagons take territorial attrition?  — **B right, A wrong**

- **A** (SUPPLY.md "Consumer 1", bullet 2): "A wagon does not supply itself. Wagons
  in hostile territory bleed, which is why a supply line is a thing you can cut."
  (ATTRITION.md check 8 says the opposite — "supply units ... are exempt" — so A
  contradicts itself across its two documents; the sim follows ATTRITION.md via
  `UnitKind::exempt_kind`, but unconditionally.)
- **B** (§3.2(a) note, §5): supply units with `domain == 0` and without the
  `0x400000` peace/assassin state `return 0` in `process_attrition` before any
  period is set; i.e. wagons never take war-time territorial attrition, but do
  take the peace/assassin periods (and are not sheltered from them).
- **Evidence** `Unit/process_attrition@005e11a0.c:299-310`:
  ```
  if (*(int *)(iVar14 + 0x218) == 0) {                 // domain == land
    if ((*(uint *)&this->field_0x68 & 0x400000) == 0) { // not peace/assassin
      ... is_supply ...; if (uVar13 != 0) return 0;      // period stays 0 (cleared at :35)
    }
    iVar14 = UnitData::get_attrition(...); ... set period ...
  }
  ```
  The peace/assassin branches set `0x400080` at :258/:290 *before* this block, so
  for them the supply exit is skipped and the period (`peace_attrition` /
  `assassin_attrition`, :262/:291) stands. `Unit/process_supply@005e0560.c:10`
  then refuses shelter on the `0x400000` bit, so a wagon bleeds at the
  peace/assassin rate and nothing cancels it. The `is_supply → 0` test at
  `process_supply:11-17` is therefore unreachable in the shipped game (war-time
  land wagons have no period; peace/assassin exits one line earlier; all supply
  types are land).
- **Verdict**: B right. SUPPLY.md's sentence is false for war-time attrition.
  `attrition.rs` is wrong in the other direction: it exempts supply units
  unconditionally (`exempt_kind` → `Outcome::Exempt(UnitKind)` at
  `attrition.rs:447`), so in the sim a wagon never bleeds even under peace or
  assassin attrition.

**Collateral finding from the same function (outside SUPPLY.md, inside A's sim):**
`process_attrition@005e11a0.c:84-135` nests the kind tests as
`if(!worker){ if(!merchant){ if(!hero){ if(!supply){ attack==0 → 0; special → 0; Spy → 0; caravan → 0 }}}} else {gathering-site check}`.
Heroes and supply units *skip* the exemptions; they do not receive one. There
is no hero test anywhere after that (`UnitData/get_attrition@00608fd0.c` has
none). So **heroes bleed** in enemy territory (Darius/Kutosov/Chandragupta
excepted, via §6 below), and the exemption set is `{attack == 0, special, Spy,
caravan}` — not "heroes, supply, spies, special, caravans" as ATTRITION.md
check 8 and `attrition.rs:153-155` state. `attack == 0` is missing from A's list.
B's §5 has this right ("heroes and supply units are *not* excused by the early
block").

### 2. Does a nation bonus grant a free supply-upgrade step?  — **B right, A wrong**

- **A** (SUPPLY.md "The radius"; `supply.rs:49-52`, `:279-281`; open question
  "Which nation the two bonus ids are"): `get_supply_upgrade` counts one step as
  held if `has_tribe_bonus(4)`, "the same bonus `FRENCH_FREE_SUPPLY` is named for".
- **B** (§2): the `if (T == BUY_SELL) level += has_tribe_bonus(4)` arm is dead
  code because `BUY_SELL = 0x2ad` lies outside the loop range `0x2fb..0x2fd`.
- **Evidence** `LeaderData/get_supply_upgrade@006e0880.c:13-34`:
  `TVar3 = SUPPLY_WAGONS_1; do { if (TVar3 == BUY_SELL) {...has_tribe_bonus(this,4)...} else has_preq(this,TVar3); TVar3 += NUM_ITEMTYPES; ... if (0x2fd < TVar3) return; }`.
  With `SUPPLY_WAGONS_1 = 763`, `NUM_ITEMTYPES = 1`, `BUY_SELL = 685` (enum dump),
  the loop visits 763, 764, 765 and the `BUY_SELL` compare can never be true.
  The identical template in `LeaderData/get_general_upgrade@006e0830.c`
  (773..775 vs 685) and `Leader/calc_attrition@006cdea0.c:19` is dead for the
  same reason — this is a shared loop macro, not a Nubian perk.
- Further: `FRENCH_FREE_SUPPLY` is read at `Build/activate@00623e20.c:857-862`
  gated on `has_tribe_bonus(...,10)` and `check_population(..., SUPPLYWAGON)`: it
  spawns a free wagon. Nothing to do with the radius. Bonus-id → nation is
  readable from the constants each id gates: `4` → `nubian_hit_points`
  (`Unit/update_hits@0060e930.c:135-138`), `10` → `french_free_supply`,
  `french_supply_heal_rate`; `0` → `aztec_move_speed`, `9` → `spanish_free_trireme`,
  `0xd` → `russian_attrition`. `LeaderData/has_tribe_bonus@006e1370.c` compares
  `tribes.list[tribe]+0x54 == id` (plus CtW racial-power bits).
- **Verdict**: B right. Radius is `14 + 2 × |{Forage, Supply, Logistics} held|`, no
  nation term. A's open question about the two ids is answered (4 = Nubia, 10 =
  France), and the bonus-4 half of it was a phantom.

### 3. Which types are supply sources  — **B right; A incomplete (silent on patriots)**

- **A**: "a unit whose type carries the supply flag"; everything else in the
  document and `supply.rs` speaks of wagons.
- **B** (§1.1): the flag is computed at load and is set for the Supply Wagon line
  *and* the three military patriots (Despot, Monarch, Comrade).
- **Evidence** `UnitType/init_final_flags@0061dc70.c:16-21`:
  `is(0x3f,0) || is(0x160,0) || is(0x162,0) || is(0x164,0)  →  field_0x2b8 |= 0x40`.
  Enum: `0x3f = SUPPLYWAGON`, `0x160 = BASE_GOV_HEROTYPES` (the Despot),
  `0x162 = THEMONARCH`, `0x164 = THECITIZEN` (the PDB's name for the third
  military patriot; B calls it the Comrade — same slot, display name differs).
  Non-strict `is`, so grafts (`SUPPLYWAGONAMER = 64`, `SUPPLYWAGONDUTCH = 65`)
  are included.
- **Consequences** (all follow from the single bit): a military patriot supplies
  at the **wagon** radius (14 + 2n) via `Supplies::find_supply`, not at his
  general radius; is himself never sheltered (`process_supply:11-17`) and never
  supply-healed (`process_healing:73-81`); takes no war-time territorial
  attrition (§1); and receives the wagon HP/speed upgrades (§8). His *general*
  radius additionally gets `mil_patriot_radius_bonus` (`HeroData/get_radius:52-81`,
  strict `is`).
- **Verdict**: B right. Behaviour-changing once the sim wires types to the flag.

### 4. What `UnitTypeData +0x218` is  — **B right on the field; A's naming wrong, effect partly wrong**

- **A**: "supply category: 0 ordinary, 1 always supplied, 2 never healed";
  `supply::Category {Ordinary, AlwaysSupplied, NeverHealed}`; "a type whose
  supply category is 2 does not heal at all".
- **B**: it is `domain` — 0 land, 1 sea, 2 air.
- **Evidence** `types.txt:41580ff` (`struct /rise.pdb/ObjectTypeData`):
  `+0x218 int domain`, between `+0x214 armor` and `+0x21c los`. Every reader is
  consistent with that: `process_attrition:147` (`== 1 → return 0`, sea never
  bleeds), `:295` (`== 2 → period/2`, air halves the special periods), `:299`
  (`== 0` gates the computed period — air never gets a computed one),
  `in_supply@00609ef0.c:13` (`!= 0 → 1`), `process_healing@005e0670.c:30-33`
  (`== 2 → return`, air never heals in this function at all), `:38-72` (`== 1` →
  the sea/carrier branch, which **returns** without ever reaching
  `find_supply`).
- **Effect on behaviour**: `in_supply` — identical (both "non-zero → in supply").
  Healing — A says only category 2 is excluded from supply healing; in fact
  **sea units never reach the supply-heal clause either** (the `domain == 1`
  branch at `:39-72` returns), so the wagon heal is land-only. (ATTRITION.md's
  "attrition mode 1 immune / mode 2 special" is the same field; its behavioural
  reading there is correct, only the name is invented.)
- **Verdict**: B right. Rename; amend the heal statement.

### 5. Preconditions on the supply heal  — **B adds, A omits; B verified**

- **A**: "Supply units do not heal this way, and a type whose supply category is
  2 does not heal at all." `supply.rs::heal_period` computes only the period.
- **B** (§4.3): the clause runs only if the unit `is_captain`, `domain != 2`,
  `has_damage(1)`, is not garrisoned (`inside_up < 0`), `domain != 1`, and
  `!is_supply()`.
- **Evidence** `process_healing@005e0670.c:21-29` (captain), `:30-33` (air),
  `:34-37` (`has_damage(1)`), `:38` (`field_0x82 < 0`, else the garrison branch
  at `:299ff`), `:39` (sea branch), `:73-81` (supply), then `:82, :234-249` the
  rate fold and `find_supply`, `:250` `repair_damage(1,1,1)`.
- **Verdict**: B right; A's document must carry these gates (the sim does not yet
  apply the heal, so only the doc changes today).

### 6. `has_general` matches the general himself  — **B right; A's implementation equivalent in practice**

- **B** (§1.4): `ObjectData::has_general` returns the unit's own index when the
  unit is a hero of type T, before searching the hero list. A is silent.
- **Evidence** `ObjectData/has_general@00646b00.c:10-27`: `is-unit (slot 0x18)
  && is_hero (0xc4) && (mask==0 || ...) && (T<0 || is(T,0)) → return own index`.
  No radius, no `is_on_map` test. Then `:37-40` the per-type count pre-check,
  `:42` `HeroesData::find_hero(..., adj)` with `adj = (x_size+y_size)*0x60` only
  for builds (`:31-35`), 0 for units.
- **Effect**: Darius/Kutosov/Chandragupta always count as supplied themselves,
  which matters because heroes *do* bleed (§1). `supply.rs::find_general`
  reaches the same answer by scanning the generals list with distance 0, except
  when the general is inactive or off-map — states in which he would not be
  processed anyway.
- **Verdict**: B right on the code; no sim change needed, worth one sentence in
  the doc.

### 7. Terra Cotta on the supplying generals  — **A right, B's aside wrong**

- **B** (§1.4 closing parenthesis): "Terra Cotta and the patriot bonuses never
  apply to those three". **A**/`supply.rs::General.terra_cotta` applies it to any
  hero.
- **Evidence** `HeroData/get_radius@00739e50.c:48-51`: `has_wonder(leader, 0x211)
  → r += terra_cotta_range`, unconditional on hero type. The patriot bonuses
  (`:52-114`) are strict-`is` on 0x160..0x165 and so indeed never apply to Darius
  et al. Shipped `TERRA_COTTA_RANGE = 0`, so nothing observable either way.
- **Verdict**: A right.
