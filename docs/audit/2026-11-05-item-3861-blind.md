# Item 3861 — four parked `RESIDUE` candidates, a blind second reading

*2026-11-05, Opus 5.5 (`claude-opus-5-5[1m]`), lane `att-3861`, on base `2c689add`.*

The question, for each of `ItemOut::draw_overlays@00677590`,
`Storm::on_field_change@00842050`, `BorderSpline::on_field_change@004a1ca0`
and `CircleRender::on_field_change@008c6db0`: does any path from code a v1
game runs enter it? Answered from the decompile export
(`~/ghidra-projects/decomp`) and the listing (`llvm-objdump -d
--x86-asm-syntax=intel` of the shipped `riseofnations.exe`) alone. **Part 1
was written and committed before the first reading (parked 3478a, 3479a,
3479b and the items' journals) was opened**; part 2 adjudicates.

The image scan is `tools/trace/report.py <exe> refs <addr>` (every `call`,
`jmp`, `jcc` rel32 to the entry at an instruction boundary, and every
four-byte copy of the address in any section, vtables named). The dispatch
scan is every `call`/`jmp dword ptr [reg + 0xNN]` (with or without an index
register) in the whole listing, each site attributed to its owning function
by the export's `INDEX.tsv`.

## Part 1 — the blind report

### `ItemOut::draw_overlays@00677590`

**Body.** `return 1;` — no reads, no writes.

**Callers.** No `call`, `jmp` or `jcc` rel32 anywhere in the image. Its
address is in two vtables, both at +0x5c:

| vtable | address | slot |
|---|---|---|
| `ItemOut::vftable` | `00b44e74` | +0x5c (`00b44ed0`) |
| `Item::vftable` | `00b44f34` | +0x5c (`00b44f90`) |

**Who installs each vtable.** `ItemOut::vftable` is written once, at
`Item::Item+0x6e` (`00677b8e`), and overwritten by `Item::vftable` at
`Item::Item+0x7b` (`00677b9b`) in the same constructor: a transient vptr.
`Item::vftable` is written by `Item::Item+0x7b`, `Item::~Item+0x1e`,
`Item::vector_deleting_destructor+0x68`, and compared (not written) by
`Console::find_item+0x75`, `Console::on_left_up+0xc05` and
`CheckSums::check_items+0x32`. So the live receiver is an `Item`.

**Where `Item`s live.** `Item::Item` has no rel32 caller; it is passed by
pointer to `_eh_vector_vbase_constructor_iterator_` from exactly two sites:
`Objects::init_item+0x88` (a new item, appended to the global `items`
array at `0x00c0a100`, list at `+0x10`) and `PtrArray<Item>::walk_data+0x29b`
(a load, into the same array). `init_item` stamps the item onto its tile as
`(+8, +10) = (0xfffd, index)` — a negative object index, so the per-tile
walk in `ObjectsOut::sort_all` (`while (-1 < o)`) never takes an item into
the object render tree `objects + 0x224`, and no item enters the
per-team object table `objects + 0x14 + who * 0x1c`. The one other home is
`ObjectsOut::sort_items`' `Tree<Item const*, int>` at `objects + 0x2dc`.

**Every dispatch through +0x5c.** The whole listing has 91 `call`/`jmp
[reg (+ idx*s) + 0x5c]` sites in 53 functions. **None of the 53 loads the
`items` global** (`0x00c0a100`–`0x00c0a113`), and none of the 36 functions
that do load it dispatches +0x5c (the intersection of the two sets is
empty). The four in `ObjectsOut::draw_overlays@00655120` are:

- the render tree `objects + 0x224` and the list at `objects + 680/692/720`
  — both index the per-team object table, which holds no item;
- `goods[select_list + 0x9e0]` and `goods[console->target_o]` — the `goods`
  array, not `items`.

`ObjectsOut::draw_underlays@00654be0` has the matching two sites on
`items[select_list + 0x9dc]` and `items[target_o]`, and they dispatch
**+0x60** (`ItemOut::draw_underlays`), not +0x5c. The item tree's only
walker that dispatches, `ObjectsOut::pop_all_zoomed_in@00655e70` (lines
222–228), dispatches **+0x58** (`ItemOut::draw`). `UnitOut::draw_orders`'
two +0x5c sites dispatch on `[this + 0xcc]` (inside `UnitData::orderlist`
at +0xc8); `Underlays::draw`'s on a texture's `[+0x30]`; the rest are
rendering, textures, streams, interface windows, Steam and lobby objects.

**Verdict: unreachable** — in any game, cheats and scenarios included. The
predicate: the only live receivers whose +0x5c is this function are `Item`s,
which live only in `items` and the `objects + 0x2dc` tree, and every
dispatch on either goes through +0x58 or +0x60 (or non-overlay slots),
never +0x5c; the overlay walker's +0x5c sites take objects and goods.

**Falsifiers.** A `cover=1` trace entering `00677590` in any game (an item
— a goody box, `Unit::explore_goody` — on screen and selected or targeted
is the case that would test it hardest); an `Item*` written into the
per-team object table or `goods` (a writer this reading did not find);
or a +0x5c dispatch site missed by the scan, which is blind only to a
computed slot (base + index) that MSVC does not emit for a virtual call.

### `Storm::on_field_change@00842050`

**Body.** `return 0;`.

**Callers.** No rel32. Its address is in one vtable: `Storm::vftable`
(`00b53f10`) +0xc (`00b53f1c`), a four-slot vtable: `scalar_deleting_destructor`,
`get_name`, `registration`, `on_field_change` — the shape of a
`BaseParamRegister` (`00b2466c`: dtor, two `purecall`s, a no-op at +0xc).

**Who installs `Storm::vftable`.** Only `Storm::scalar_deleting_destructor+0x21`
(`004999b1`) and `Storm::~Storm+0x1e` (`0084292e`): the destructors' vptr
reset. **There is no constructor**: the export has no `Storm::Storm` and no
`StormOut::StormOut`, no other `.text` copy of `00b53f10` exists, and the
only reference to `Storm::scalar_deleting_destructor` is its own vtable's
slot 0; `Storm::~Storm` is dead (no reference at all). `StormOut` has no
vtable in the export. `StormOut::registration@00842070` — the function that
registers storm fields with the parameter window (`ParamRegisterWindow::registration`
at `+0x84f` and `+0x884`) — has **no reference anywhere** (`refs`: dead).
`Storm::registration@00842060` is `return;`.

**Verdict: unreachable** — in any game, the cheat-gated parameter window
included. The predicate: no live object ever carries `Storm::vftable`
(it is installed only by destructors of a class nothing constructs), so
no dispatch through any slot can reach this function.

**Falsifiers.** A `cover=1` trace entering `00842050`, `00842070` or
`00499990`; any write of `00b53f10` outside the two destructors (the scan
found none, at any byte offset of any section).

### `BorderSpline::on_field_change@004a1ca0` and `CircleRender::on_field_change@008c6db0`

The two share one path and one verdict.

**Bodies.** `BorderSpline::on_field_change` sets `this->field_change = 1`;
`CircleRender::on_field_change` calls `CircleRender::init_circle(this)`
(its only other caller is `CircleRender::init+0x30`).

**Callers.** No rel32 to either. Each is +0xc of its own four-slot
`BaseParamRegister` vtable: `BorderSpline::vftable` (`00b5419c`, slot
`00b541a8`) and `CircleRender::vftable` (`00b38c9c`, slot `00b38ca8`).

**Live receivers.** `BorderSpline::vftable` is written only by
`BorderSpline::BorderSpline+0x4e`, called only from `BordersData::BordersData+0xba`
(the `borders` global's dynamic initializer and `Borders::Borders`): the
`spline` member at `BordersData + 0x38`. `CircleRender::vftable` is written
only by `CircleRender::CircleRender+0x3c`, called only from the
`circle_gen` global's dynamic initializer. Both objects exist in every
process.

**Every dispatch through +0xc on a `BaseParamRegister`.** A
`BaseParamRegister*` is stored polymorphically in exactly one place: the
parameter window's category registry `ParamRegisterWindow::obj_cats`,
filled by `ParamRegisterWindow::registration`. Both objects are registered
in every game:

- `circle_gen`: `Game::init` (decompile line 847,
  `registration(param_register_win, &circle_gen, …)`).
- `borders->spline`: `Borders::init+0x97` (`00883437`) after `lea esi,
  [edi + 0x38]` and a +0x8 dispatch (`BorderSpline::registration`) on it.

`obj_cats` is read only by `ParamRegisterWindow` methods (twelve
functions, all in the class). The listing of `ParamRegisterWindow`
(`009339f0`–`00935900`) has **seven** `call [eax + 0xc]` sites, each on
the current object `obj_cats[cur_cat]->list[cur_obj]` after a field write:

- `on_scroll@009343b0` ×5 (`93442f`, `93448b`, `9344c7`, `934502`, `93452f`),
- `on_combobox_select@00934550` (`9345ca`),
- `on_change_edit_box@009345e0` (`934744`), also called from `on_key_down+0x27`.

All three are input handlers (vtable slots +0x330 and +0x398, and the edit
box's change); none is called from a frame, a load or a registration
(`LoadGame::load_game` and `Game::init` call only `init` and `registration`,
neither of which dispatches +0xc; `registration`'s one indirect call is
slot 0 of an `Array`).

**Who opens the window.** `MiscAccess::param_register_win` is constructed in
every game (`Game::init_console`, line 124). It is shown only by
`ParamRegisterWindow::exec@00934c30` (`set_modal` and a show), whose callers
are `ConquestWin::on_key_click+0x5aa` (Conquest the World, cut) and
`Console::exec_keymap+0x4c5` (`007c31a5`), **keymap command `0x1e`**, under
`console->cheat_keys != 0 && (semaphore & 4) == 0`. `cheat_keys`
(`Console + 0x1cf0`) is written by:

- `Console::Console` — 0 (the low dword of a 16-byte store whose next three
  dwords are `click_drag_timing` 7, `low` 0x14, `high` 0x40);
- `System::init` (`59980c`) — `prefs2_get(<key at loc+0x1eff0>, 0)`, default
  **0** (`push 0x0` at `5997ee`);
- `ConsoleWin::run_cmd` case `0x11` — the cheat console command, 1 or a
  parsed value, when `(semaphore & 0x14) != 4`;
- `ConquestWin::exec_cheats` (cut).

**Verdict: reachable, but only through the cheat-gated debug parameter
window.** The path: cheat keys on (a `prefs2` entry, or the in-game console's
cheat command `0x11`) → the key bound to keymap command `0x1e` →
`ParamRegisterWindow::exec` → a human picks the "borders" or the circle
object in the window and edits a field (combo, edit box or scroll) →
`+0xc` on the registered object. No game without `cheat_keys` and a human
editing a field in that window enters either function; no frame, no load,
no AI and no unattended capture does. Whether that debug tool is part of
"a v1 game" is a direction call, not a reading: the cut list names neither
the cheat console nor the parameter window, and the window is built in
every game.

**Not settled.** Whether keymap command `0x1e` is bound to any key in the
shipped keymap (the install's key-binding data was not read); if it is
unbound, the path also needs a user-edited keymap.

**Falsifiers.** A `cover=1` trace entering `004a1ca0` or `008c6db0` in a game
with `cheat_keys` off (it would name a dispatcher this reading missed); a
`+0xc` dispatch on an `obj_cats` entry outside `ParamRegisterWindow`; a
second polymorphic store of `&circle_gen` or `&borders->spline`. And the
positive falsifier of "unreachable": a traced game with cheats on that
opens the window and edits the border spline's `breadth` enters
`004a1ca0`.
