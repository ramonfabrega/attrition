# Audit: the command payload encoding, blind second reading

**Date:** 2026-08-24. **Mechanic:** `CommandPackage.data`'s command format
(`docs/COMMANDS.md`, `crates/rondata/src/commands.rs`). **Method:** the
standing pattern — the first reader (Fable, same session) wrote the document
from the Ghidra export and verified it against the heavengames sample; a
blind second reader (Opus, isolated worktree branched from `main`, which
carries neither the document nor the queue entry) re-derived the encoding
from the export alone, 886 lines, every claim cited `Class::method@addr` and
marked HIGH/MEDIUM/LOW; this pass adjudicated every disagreement back to the
decompile. The blind report lived in the job's tmp and is not kept in-repo;
everything it added is absorbed below and into COMMANDS.md's amendments.

## Where the readings agreed, independently

- **The dispatch table, all 82 entries, 0x00–0x51 with no holes**, and every
  size — each reading derived them twice over (decode-side `process_*`
  returns, encode-side `add_command` size arguments) and the four tables
  coincide entry for entry.
- The framing: no count, no length prefix, no delimiter — the type byte
  alone sizes the record; `process_all` walks `p += n + gap`, clears
  `valid` last.
- The packed-from-+0x1 rule, and the one struct-vs-wire exception both
  readings found on their own: `LeaderOptionsCommand` travels as 0x21
  packed bytes against `types.txt`'s aligned 0x24.
- The three variable-length encodings with identical formulas (group
  3+2·num, chat 0x13+2·len with the NUL on the wire and `len` excluding
  it, spline 6+8·len dropping the source's z), and group's degenerate
  3-byte `num = 0` "same selection as last" form, resolved through the
  per-player `last_num/objects/uids_received` state with its send-side
  mirror.
- The selection model: a group command stashes `Groups::push_group`'s index
  in `CommandPackage.group` (+0x0c) and every unit handler reads it.
- The obfuscation layer, in full: the u16 XOR with `(seed >> 8) & 0xffff`
  living in `CommandPackage::send` (odd tail byte plain — explicit on send,
  implicit in `process_all`'s `size/2` loop count), the 0-or-1
  uninitialised gap bytes from `Random::get(0, 2)` seeded `info.seed` on
  both ends, both gated on `semaphore.ptr[0] & 4`, and the receive handler
  (`process_command_package_data`) storing wire bytes undecoded — so
  `write_package` before `process_all` means **SP recordings are plain and
  MP recordings are obfuscated**, each reading proving it from the call
  ordering independently.
- The `UngracefulPlayerDrop` exemption (`data[0] == 'P'`, size ≤ 4, bits
  0x14) and its reason: `DropControl::process_drops` synthesises the
  package locally and writes it plain.
- `valid`'s lifecycle: armed once by `CommandManager::init`, per-package by
  the net handler, cleared by `process_all` — the sample's
  first-record-only `valid = 1` explained the same way twice.
- Both readings flagged the same decompiler artifact in `send`'s unrolled
  XOR loop (`this[-0x6170].data + ...`, an impossible source pointer) and
  read past it to the same conclusion.

## Verdicts on the disagreements

1. **`ConsoleCmd` (0x4e) can never travel — second reading right, document
   corrected.** Its wire size 0x209 = 521 exceeds `add_command`'s
   `param_2 + size > 0x200` rejection even into an empty package, so
   `issue_console_cmd`'s append always fails; and the adjudication's own
   sweep of every `add_command` caller in the export (Options, GroupOut,
   TurnControl, BuildOut, UnitOut, IFaceDiploBase, Console, DropControl)
   found nothing else emitting 0x4e — `Console::on_key_down` emits
   *hotkey* (0x22) commands. The first reading's "the `~` console travels
   in lockstep" is wrong: the dispatcher handles a command nothing can
   send. COMMANDS.md §4 amended.
2. **The save-game walker serialises `group` — second reading right,
   document corrected.** `CommandPackage::walk_data` (0x94b740) walks
   `[this, this->data)` = 0x12 bytes: `stamp, play, valid, group, size`
   (confirmed against `CommandManager::walk_data`'s literal addresses,
   0xe8ff9a − 0xe8ff88 = 0x12). Only the *recording* head
   (`write_package`, 18 bytes, `frame` in place of `group`) drops it. The
   first reading's §6 said `walk_data` confirms group is never serialised —
   true for recordings, wrong for save games. Amended.
3. **`move_near`, `repair`, `board_ship`, `begin`, `cheat_init_unit` have
   no issuer at all — second reading right, document corrected.** The
   first reading guessed the three missing `issue_*` wrappers meant direct
   UI/AI call sites. The blind reading found none anywhere, and the
   adjudication's independent sweep of all 36 outside `add_command`
   callers confirms it: every one emits an already-tabled type, none of
   these five. They are dispatched-but-never-emitted (legacy or cut
   paths); their wire formats remain pinned by `process_*`. §6 amended.
4. **The `LeaderOptions` tail is `BitMask<32>` — second reading right on
   the name.** The PDB's `LeaderOptionData` +0x10 field is `BitMask<32>`
   (16 bytes); the first reading quoted the decompiler's stack local
   `BitMask<8>` in `issue_leader_option`. Same 16 raw bytes either way.
   §4 amended.
5. **`write_package` call sites — first reading right on the count,
   nothing changes.** The blind reading says exactly three sites
   (process_turn SP, process_turn MP, process_drops); there is a fourth —
   `process_turn`'s invalid-package error path also writes the offending
   package (behind the same recording bit) before halting the game. All
   four run before `process_all`, so every conclusion about recordings
   storing pre-decode bytes stands unchanged.

## What the second reading added (adopted)

- **Bit 4's only writer is `Game::run_gamespy` (0x587060)** — verified
  (`ptr[0] |= 4`, clearing 0x10 alongside): the obfuscation gate is
  precisely "network game", not a looser multiplayer notion.
- **Recordings are self-decrypting**: the header's Game stretch carries
  both `GameInfo.seed` and the whole semaphore, so playback restores bit 4
  itself; `run_playback` ORs in 0x10 (producing the 0x14 the drop
  exemption tests), and `read_package` at EOF clears 0x10 and 0x04 and
  sets `ptr[3] |= 1`.
- **A mode fingerprint in `valid`**: an SP recording has `valid = 1` on
  the first package only; an MP recording has it on every wire package
  (the net handler arms each) with the synthesised drop packages at 0 —
  a reader can classify a recording without parsing payloads.
- The receive-side selection state is bounded: `last_objects_received` /
  `last_uids_received` are `[8][128]` — a 128-object cap per selection,
  with `add_group` clamping to the same shape.
- `add_chat`'s cap is one byte stricter than `add_command`'s
  (`>= 0x200` vs `> 0x200`).
- `read_package`'s third argument is a play filter (seek back 8 when the
  next package's `play` differs) — the loop MP-playback's
  `send_local_package` uses to re-send one player's stream at a time.
- `semaphore.ptr[3] & 2` (in `process_all`'s exemption) has no writer in
  the export, so that term of the gate is constant-true in practice.

## What stays open

Unchanged from COMMANDS.md §6: no MP sample has exercised `decode_mp`;
`marwan`'s semantics are unread past its size. `begin`'s status improves
from "no issue site found" to "provably never emitted" (verdict 3).
