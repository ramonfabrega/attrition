# Adjudication: COSTS — Reading A (docs/COSTS.md + crates/sim/src/cost.rs) vs Reading B (rederive-costs.md)

Every verdict below was settled by re-reading the decompilation at
`~/ghidra-projects/decomp/funcs/` (and `types.txt`) and, where the claim is
about data, the user's own `game/data/*.xml`. Cited as `Class/method@addr.c:line`.
Offsets: `L+0xNNN` = Leader field; `UT+0xNNN` = UnitTypeData/ObjectTypeData field.

Summary: **9 behaviour-changing disagreements** (B right on 8, A right on 0,
one is an impl-vs-original slip that neither document states); **12 places
where B extends or closes something A left open**, all verified; and a long
list of doubly-confirmed arithmetic.

## Part 1 — Disagreements (behaviour-changing)

### D1. The redirect table and its rates — **B right, A wrong (and the implementation with it)**

- **A:** The redirect reads the four `*_SUPPORT_GOOD`/`*_SUPPORT_RATE`
  columns of `resourcerules.xml`; the undiscovered table is Food→Wealth,
  Timber→Wealth, Wealth→Wealth, Knowledge→Food, Metal→Timber, Oil→Wealth, all
  at rate 1/1 (256); obsolete is Wealth 1/1 for all six. `Redirects::RON` in
  `cost.rs:311-335` encodes exactly that. The doc's worked examples follow:
  Mathematics (`8k`) = 80 food before Classical; Militia (`8m`) = 80 timber.
- **B:** The redirect reads `UNDISC_COST_GOOD/RATE` and `OBS_COST_GOOD/RATE`
  (`GoodTypeData +0x2b4/+0x2c8`, `+0x2b8/+0x2cc`). Undiscovered: Knowledge→Food
  ×3/2, Metal→Timber ×5/4, Oil→Metal ×3/2, Food/Timber/Wealth→Wealth ×3/2.
  Obsolete: Timber→Oil ×1/2, all others Wealth ×1/1.
- **Evidence:**
  - `TypeData/get_cost@00664090.c:1575-1600` — the tail loop reads
    `*(int *)(goodtypes[g] + 0x2b4)` / `+0x2c8` when `has_preq(g)==0`, else
    `+0x2b8` / `+0x2cc`.
  - `types.txt:41556-41565` names them: `+0x2b4 undiscovered_cost_good`,
    `+0x2b8 obsolete_cost_good`, `+0x2bc undiscovered_support_good`,
    `+0x2c0 obsolete_support_good`, `+0x2c8 undiscovered_cost_rate`,
    `+0x2cc obsolete_cost_rate`, `+0x2d0 undiscovered_support_rate`,
    `+0x2d4 obsolete_support_rate`.
  - `GoodType/init@0066ea20.c:188-230` loads them in that order via
    `Types::good_key` / `String::fraction(msg,0x100)` (8.8).
  - Data (`game/data/resourcerules.xml`): Food :41-44 `Wealth 3/2 | Wealth 1/1`;
    Timber :74-77 `Wealth 3/2 | Oil 1/2`; Wealth :107-110 `Wealth 3/2 | Wealth 1/1`;
    Knowledge :140-143 `Food 3/2 | Wealth 1/1`; Metal :173-176 `Timber 5/4 | Wealth 1/1`;
    Oil :206-209 `Metal 3/2 | Wealth 1/1`. The `*_SUPPORT_GOOD/RATE` columns
    (all 1/1, Oil→Wealth) are what A transcribed; `grep` over the whole decomp
    finds **no reader** of `+0x2bc/+0x2c0/+0x2d0/+0x2d4` in `get_cost` at all —
    the only hits on those offsets are unrelated `buildtypes +0x2c0` reads.
- **Verdict: B right.** Consequences: Mathematics before Classical is
  `(80*384)>>8 = 120` food (not 80); a Militia's `8m` is `(80*320)>>8 = 100`
  timber (not 80); anything priced in oil before Industrial is charged in
  **metal** ×3/2 (not wealth). `Redirects::RON` must change to rates
  `[384,384,384,384,320,384]` with Oil→Metal, and obsolete Timber→Oil rate 128;
  the test `metal_is_charged_as_timber_until_it_is_available` expects timber 30
  and must expect `(30*320)>>8 = 37`. A's "Support means cost" section must
  stop claiming the four `*_SUPPORT_GOOD/RATE` fields are read by the cost
  path — they are not read anywhere found. (The obsolete table is inert in
  stock data: every good's `<OBS>` is `disable`, resourcerules.xml:27 etc.)

### D2. Redirect chaining — **B right**

- **A:** "Nothing else in the shipped table points at an unavailable good, so
  one pass is exact." `charges()` in `cost.rs:375-383` does one pass and only
  adds a redirect when the *target* is available.
- **B:** The redirected amount is a recursive `get_cost(g, …, include_redirect=1)`,
  so Oil→Metal→Timber chains.
- **Evidence:** `get_cost@00664090.c:1590-1592` calls vtable slot `0x78`
  (`get_cost`) on the missing good with `param_6 = 1`. With the real table
  (D1) Oil→Metal, and Metal is itself unavailable until Classical, so in the
  Ancient age an oil price is added into the metal price, which is then
  redirected into timber at 5/4 — the original also adds the redirected amount
  to `cost` for the priced resource regardless of that resource's own
  availability; `pay_cost` then charges only available ones.
- **Verdict: B right.** Only reachable for oil-priced items before Classical
  (none shipped), so it is a correctness note rather than a stock-game bug, but
  `charges()` should either recurse or document the single pass as a stated
  simplification.

### D3. Population cap indexes `POP_CAP` by **military tech level**, not age — **B right**

- **A:** `cap = POP_CAP[age]`; "Twenty-five in the Ancient age, two hundred in
  the Information age, and the age table is the whole of it." `pop_cap(t, age, …)`
  in `cost.rs:533`.
- **B:** `mil = epoch[0]` (military library level 0..7) indexes `pop_cap[]`.
- **Evidence:** `Leader/calc_pop_cap@006dc490.c:31-32`:
  `uVar6 = *(uint *)(leaders.list[iVar5].field_0x6eb8 + 0xe8) ^ 0x63187; iVar4 = constants->pop_cap[uVar6]`.
  `types.txt:42445-42458`: `LeaderDataEncrypt +0xdc ages`, `+0xe8 int[4] epoch`.
  `LeaderData/compute_epoch@006d6f80.c:14-24`: index 0 walks
  `BASE_MILITARYTYPES` counting `has_tech` — `epoch[0]` is the Military 1–7
  line. The later `uVar6 == 7`, `> 3`, `> 5` clauses use the same variable.
- **Verdict: B right.** The shipped game's pop cap rises with each Military
  tech (25 → 50 on Military 1), not with the age. `docs/COSTS.md` §Population
  and the `age` parameter of `pop_cap()` must be renamed and re-described;
  the test `the_population_cap_is_the_age_table_clamped_by_the_lobby` is
  numerically still right but misnamed.

### D4. Ramp ceiling class for caravans (and merchant fleets) — **B right**

- **A:** `UNIT_WORKER_RAMP_MAX` (500%) = citizens, merchants;
  `UNIT_OTHER_CIVILIAN_RAMP_MAX` (200%) = generals, spies, supply wagons,
  **caravans**.
- **B:** Citizen/Scholar/`is_merchant`/`unit_flags2 & 8` → worker 500%;
  then `obj_masks & 4` → other-civilian 200%; else military.
- **Evidence:** `get_cost@00664090.c:600-622`: after the
  citizen/scholar/`is_merchant` test, `uVar19 = extraout_ECX_00[0xae] & 8`
  (= `UT+0x2b8 unit_flags2 & 8`) `goto LAB_0066569a` (worker); only then
  `[0x79] & 4` (= `+0x1e4 obj_masks`, letter **C** = Civilian per
  unitrules.xml:24) picks other-civilian vs military.
  `UnitType/init_final_flags@0061dc70.c:26-29`: bit 8 of `unit_flags2` is set
  for `is(0x3b Caravan,0) || is(0x13e Merchant Fleet,0)`.
  `unitrules.xml:625` Caravan `OBJ_MASK MWCP` (C set, but the flags2 test wins first).
- **Verdict: B right.** Caravans and merchant fleets ramp to 500%, not 200%.
  Generals (`MCP`, :340), spies (`FCP`, :568) and supply wagons (`VC`, :853)
  are civilian → 200% as A says. The doc's class table needs caravans moved
  and merchant fleets added; `RampClass` itself is fine (callers classify).

### D5. Citizen and scholar counts include militia — **B right, A omits**

- **A:** count = `num_queued[type] + num_units[type]` (+ nukes used, − free bombers).
- **B:** for Citizen/Korean citizen, `n += count(0x42)+count(0x43)+count(0x44) − scholar_militia`;
  for Scholar/Korean scholar, `n += scholar_militia`; additionally
  `is(0x13b,0)` adds `nukes_used` again.
- **Evidence:** `get_cost@00664090.c:565-580`:
  `param_7 = param_7 + (iVar13 - field_0x9f0) + iVar9 + iVar11` for
  `BASE_UNITTYPES/PEASANTSKOREAN`, `param_7 += field_0x9f0` for
  `SCHOLARS/SCHOLARSKOREAN`, `param_7 += field_0x7bc` when `is(0x13b,0)`.
  `Leader/track_unit_type@006e0dd0.c:60-68` increments `+0x9f0` when a
  militia-class unit was made from a scholar.
- **Verdict: B right.** Citizens converted to militia/minutemen/partisans still
  count in the citizen ramp (minus the ones that were scholars, which count for
  scholars instead). A's `Counts` does not carry this; the doc must state it.
  Nuclear missiles count `nukes_used` twice (once in `get_support_count@006da110.c:31-33`,
  once here) — an original quirk worth recording.

### D6. Group counting requires `attack != 0` — **B right, A omits**

- **A:** PROGRESSION bit 0 → count the production group.
- **B:** bit 0 **and** `attack != 0`; otherwise falls through to the type count.
- **Evidence:** `LeaderData/get_support_count@006da110.c:15`:
  `if (((*(byte *)(iVar1 + 0x2f4) & 1) != 0) && (*(int *)(iVar1 + 0x1e8) != 0))`;
  `types.txt` `+0x1e8 attack`. Same gate in `track_unit_type@006e0dd0.c:16`
  for maintaining the group counters.
- **Verdict: B right.** No shipped non-attacking unit has bit 0 set as far as
  checked (supply wagon is PROGRESSION 0), so inert in stock data, but it is
  the rule and should be stated.

### D7. Placement of several discounts relative to the ramp — **B right, A's doc imprecise**

- **A (doc):** "Between the base price and the ramp sits a tail of about forty
  adjustments … with three exceptions every one is `cost*(100-X)/100`"; the
  governments list includes Monarchy and Socialism. (The impl's `Modifiers`
  does have a `late_discount` slot, described as "Sugar, Coal, Gold, Iron and
  Gypsum".)
- **B:** After the ramp, in order: `MILITARY_UNIT_DISCOUNT`, Monarchy (stable),
  Socialism (siege/airbase/dock), Salmon (sea); then the common tail: Coal /
  Sugar / Gold / Iron by resource, Gypsum, unassimilated ×2, Supercollider,
  Indians-elephants, redirect.
- **Evidence:** `get_cost@00664090.c:625-677` (after the support-slot loop
  ends at :623): military_unit_discount, `MONARCHY_1|2 && where==0x1ac`,
  `SOCIALISM_1 && where∈{0x1ae,0x1bf,0x1b0}`, salmon (`+0x6da9&1 && domain==1`);
  then `:1473-1505` coal/sugar/gold/iron, gypsum; `:1506-1525` unassimilated
  ×2 (units only); `:1526-1552` Supercollider `(100+super_missiles)×cost/100`
  per enemy; `:1553-1574` Indians; `:1575` redirect.
- **Verdict: B right.** Behaviour-changing for anyone mapping Monarchy /
  Socialism / Salmon / the military-level discount into `Modifiers.discount`
  (pre-ramp) — they belong in `late_discount`. The doc's sentence must be
  corrected; the code's two-slot model can express it.

### D8. Scaling of the military discounts for short games — **B right**

- **A:** `discount * ages / 8` for both `MILITARY_UNIT_DISCOUNT` and `MILITARY_UPGRADE_DISCOUNT`.
- **B:** `(ages×pct + 7) >> 3` (ceiling), and for the *unit* (training) discount
  additionally `max(1, …)`; the unit discount uses `max(unit.military_level,1)`.
- **Evidence:** `get_cost@00664090.c:536-540` (upgrade):
  `iVar9 = iVar13*iVar9 + 7; iVar9 = (iVar9 + (iVar9>>0x1f & 7)) >> 3`;
  `:636-646` (unit): same plus `if (iVar9 < 1) iVar9 = 1;` guarded by
  `if (iVar9 < 1) iVar9 = 1;` on the level at :632.
- **Verdict: B right.** Also both discounts compare against `epoch[0]` (the
  military *tech* level, `+0xe8 ^ 0x63187`), not the player's age — A's
  phrase "per military level the player's age is ahead of the unit's" should
  read "per Military tech level the player holds above the unit's".

### D9. `can_pay_cost` early return — **neither document; impl deviates**

- **A (impl):** `if n <= 0 { return 0 }` (`cost.rs:418`).
- **B:** `if k == 0 return 0`; a negative quotient (escrow > stock) neither
  returns 0 nor raises `best`.
- **Evidence:** `TypeData/can_pay_cost@00667570.c:77-80`:
  `iVar3 = (int)uVar4 / iVar3; if (iVar3 == 0) return 0; if (iVar6 < iVar3) iVar6 = iVar3;`.
- **Verdict: B right about the original.** `cost.rs` returns 0 where the
  original returns −1 (or the other resources' max). Only reachable when
  `bucket < escrow`; worth a one-line fix or a stated deviation.
