# Item 3859 — two map-generation functions, a blind second reading

*2026-11-05, Opus 5.5 (`claude-opus-5-5[1m]`), lane `att-3859`, on base `a013b79d`.*

The question, for each of `Map::make_continents@00694ab0` and
`Map::force_continent_spacing@0068e6a0`: does any path from code a v1 game
runs enter it? Answered from the decompile export (`~/ghidra-projects/decomp`)
and the listing (`llvm-objdump -d -M intel` of the shipped
`riseofnations.exe`) alone. **Part 1 was written and committed before the
first reading (MAPGEN §18, parked 3856c) was opened**; part 2 adjudicates.

The image scan is `tools/trace/report.py <exe> refs <addr>` (every `call`,
`jmp`, `jcc` rel32 to the entry at an instruction boundary, and every
four-byte copy of the address in any section, vtables named). The dispatch
scan is every `call dword ptr [reg + 0xNN]` and `jmp dword ptr [reg + 0xNN]`
in `.text`'s listing, each site attributed to its owning function by the
export's `INDEX.tsv`.

## Part 1 — the blind report

### `Map::make_continents@00694ab0`

**Callers.** No `call`, `jmp` or `jcc` rel32 anywhere in the image. Its
address appears exactly twice, both in `.rdata`:

| vtable | address | slot |
|---|---|---|
| `MapScenario::vftable` | `00b4549c` | +0x40 (`00b454dc`) |
| `Map::vftable` | `00b45d68` | +0x40 (`00b45da8`) |

Every other `Map` subclass's +0x40 is its own override (`MapConquest`,
`MapConquestSea` → `MapConquest::make_continents`, `MapGrass`, the eighteen
random-map styles, `MapGreatLakes`). No override calls the base by rel32:
the scan finds none.

**Who installs each vtable.** `Map::vftable` is written only by `Map::Map+0x2e`
(`006a070e`) and `Map::~Map+0x25` (`0047b955`): the base constructor's and
destructor's transient vptr. Neither function makes a virtual call
(`Map::Map@006a06e0` and `Map::~Map@0047b930` have no `code **` dispatch in
the export), and every construction site in `Map::new_map@006a0950`
overwrites the vptr straight after `Map(pMVar3)` returns. **So no live object
has `Map::vftable` when anything dispatches.** `MapScenario::vftable` is
written once, at `Map::new_map+0x673` (`006a0fc3`): case `0x1a`,
`type = SCENARIO_MAP`.

**Every dispatch through +0x40 on a map.** In the whole listing, +0x40 calls
whose owner is a `Map*` class are exactly two:

- `Map::make@0068bc90`, at `0068bdfb`, unconditional, after `load_map_data`.
- `Map::run_map_script@0068c870`, at `0068c8d7`, unconditional.

(The other `Map`-adjacent +0x40 sites — `ConquestMap::cut_up_render_land`,
`ConquestMap::init_land`, `WorldMap::*`, `WorldMapBackground::render`,
`MiscAccess::device_lost_reset`, `TerrainOut::*` — dispatch on textures,
backgrounds and streams, never on a `Map`.)

**Can the receiver be a `MapScenario` at either?**

- `Map::make` is the +0x64 of every vtable *except* `MapScenario`'s, whose
  +0x64 is `MapScenario::make@0068c8f0` (`vtables.txt`, and `refs 0068bc90`
  lists 21 `.rdata` copies with `MapScenario::vftable` absent).
  `MapScenario::make` makes four virtual calls, all through +0xac on objects
  drawn from `GameAccess::objects` — none on `this`, none at +0x40. The
  only +0x64 dispatches on a fresh map are `Setup::build_game+0x4a1`
  (`(**(game_map + 100))(num_nations, -1, param_1)`) and
  `ConquestGame::build_conquest_game` straight after `new_map`, and the
  same expression in `ScenarioEditor::generate_map@009a0950` (
  line 276). A scenario map dispatched there runs `MapScenario::make`, not
  `Map::make`.
- `Map::run_map_script` is at +0x68 of every map vtable, `MapScenario`'s
  included — but **nothing in the image dispatches +0x68 on a map**. All 343
  `call [reg + 0x68]` sites and the one `jmp [reg + 0x68]`
  (`OnlineService::lobby_get_lobbies`, `00a3cbb9`) were attributed: none is
  owned by a `Map*` class; the `Setup::build_units` and
  `ConquestGame::build_units`/`build_cities` sites dispatch on a `Type *`
  drawn from `types.list`; the rest are interface windows, the editor
  (`IFaceEditor*`), GameSpy, leaders and groups. `run_map_script` has no
  rel32 caller either (`refs 0068c870`: pointers only, 22 vtables).

**Verdict: unreachable.** The predicate that keeps it out: the only receiver
whose +0x40 is `Map::make_continents` while live is a `MapScenario`
(`new_map` case `0x1a`), and a `MapScenario`'s +0x64 is `MapScenario::make`,
which does not dispatch +0x40, while its +0x68 (`Map::run_map_script`, the
other +0x40 dispatcher) has no dispatch site at all. This holds in a
scenario load too — the verdict does not depend on scenarios being cut from
v1.

**Falsifiers.** Any trace (`tools/trace`, function coverage) entering
`00694ab0` or `0068c870`, in any game — a scenario (`SCENARIO_MAP`) load is
the one that would test it hardest; the `map.cpp` checksum line `0x1e7f`
(`GameLog::say_checksum` after the +0x40 call in `Map::make`) printed in a
scenario game's gamelog; or an instance of `MapScenario` whose +0x64 is
dispatched from a site not listed above. A missing dispatch site is the
scan's one blind spot: a vptr loaded and called through a register offset
the decompiler and the listing both print as something other than
`[reg + 0x40]` / `[reg + 0x68]` (e.g. a computed slot), which MSVC does not
emit for a virtual call.

### `Map::force_continent_spacing@0068e6a0`

**Callers.** One rel32 call, from `ScenarioEditor::import_image+0x4f0`
(`009a4420`). Its address is in no vtable and no section copy: it is
`__cdecl`/static (the mangled unwind name `force_continent_spacing_Map__SAXH_Z`
says `static void (int)`).

**Callers of `ScenarioEditor::import_image@009a3f30`.** Two rel32 calls:

- `ScenarioEditor::generate_map+0x620` (`009a0f70`) — the scenario editor,
  cut from v1.
- `MapConquest::make_continents+0x5a2` (`0068e142`) — on the path to it,
  unconditionally after an `ImageIO::load` of a `conquest\` image.

**Can a v1 game enter `MapConquest::make_continents@0068dba0`?** It is +0x40
of `MapConquest::vftable` and `MapConquestSea::vftable`, installed only by
`new_map` cases `0x18` (`CONQUEST_MAP`) and `0x19` (`MapConquestSea` ctor).
`new_map`'s style is its `ecx`: from `Setup::build_game` it is
`[world + 0x30]` (`5ac625`–`5ac62b`), whose writers are
`Game::init_rules_and_teams` (`set_map(info.map_style)`, the byte at
`info + 0x25`, `589ce1`), `Setup::build_game` itself (`0x17` under the
semaphore flags, then the map's own type) and
`ScenarioEditor::generate_map`. `set_map` draws `6 + r % 17` — styles 6
through 22 — for every random pick (cases 0–5), and passes any other value
through unchanged. `ConquestGame::build_conquest_game` mints `0x18`/`0x19`
itself (`(map_style == 8) * 2 + 0x18`, and `0x19` for a sea link). The
function reads `GameAccess::conquest_game` throughout (`start_who`,
`player_tribe`, `conquest_leaders`, `conquest_countries`, `link`) and reports
`"No conquest map data available."` when `conquest_win` is null.

**Verdict: unreachable in v1.** The predicate: the two entries are the
scenario editor's `generate_map` and `MapConquest::make_continents`, whose
receiver exists only for map style `0x18`/`0x19`, which only Conquest the
World's `build_conquest_game` writes. Both are on CLAUDE.md's cut list.

**What this reading does not settle.** Whether the v1 lobby can write
`info.map_style` = `0x18` or `0x19` directly (a skirmish lobby offering
"Conquest" as a style), which `set_map`'s pass-through would carry to
`new_map` with no Conquest state behind it. The function's own error path
says such a game was not meant to exist, but the export read here does not
enumerate the lobby's style list. **Falsifier**: a trace entering
`0068dba0`, `009a3f30` or `0068e6a0` from `Setup::build_game` in a skirmish
game; or the lobby's map-style list (the setup window's combo, or
`map_file_mapping`'s rows) holding the conquest entries as selectable.

## Part 2 — adjudication

*(Written after part 1 was committed.)*

The first reading is MAPGEN §18.1 (item 3856) and parked 3856c. Each claim
beside the blind one:

### `Map::make_continents@00694ab0`

| claim | first reading (3856) | blind (3859) | verdict |
|---|---|---|---|
| homes of the address | `Map::vftable` and `MapScenario::vftable` +0x40 | the same two, `00b45da8` and `00b454dc`; no rel32 | **agree**; pinned in `every_unreferenced_row_is_unreferenced_in_the_image` |
| `Map::vftable` is never live | no `new_map` case leaves it installed | written only by `Map::Map+0x2e` and `Map::~Map+0x25`, neither of which dispatches | **agree**; the blind reading adds the destructor |
| `MapScenario::make` dispatches no +0x40 | listing `0x68c8f0..0x68d1a0` has no indirect call through +0x40/+0x64/+0x68 | its four indirect calls are all `+0xac` on `GameAccess::objects` entries | **agree** |
| +0x64 dispatchers on a map | `Setup::build_game` line 271, with `ScenarioEditor::generate_map` | the same, plus `ConquestGame::build_conquest_game` on its local `new_map` result | **agree on the verdict**; the conquest site mints only styles 0x18/0x19 (`(map_style == 8) * 2 + 0x18`), never 0x1a, so it cannot hold a `MapScenario` |
| `Map::run_map_script` (+0x68) | "no dispatch on `game_map` in the export" | no `call`/`jmp [reg + 0x68]` in the whole listing is owned by a `Map*` class or has a map receiver (343 calls and one jump attributed) | **agree**; the blind reading's scan is the stronger claim — the export's silence on `game_map` would not exclude a dispatch through a local `Map *` |

**Settled: unreachable.** Both readings name the same predicate. It is a
`blind::RESIDUE` row (`0x0069_4ab0`), and the `Blind:` line's residue
count moves 208 → 209, open 47 → 46 (the commander's line).

### `Map::force_continent_spacing@0068e6a0`

| claim | first reading (3856) | blind (3859) | verdict |
|---|---|---|---|
| callers of the function | one, `ScenarioEditor::import_image@009a3f30` at `0x9a4420` | the same | **agree** |
| callers of `import_image` | (not asked — "only the editor's image import calls it", the editor being cut) | **two**: `ScenarioEditor::generate_map+0x620` (`009a0f70`) **and `MapConquest::make_continents+0x5a2` (`0068e142`)** | **disagree, settled for the blind reading** by `report.py <exe> refs 009a3f30`: two rel32 call sites, both at instruction boundaries. The first reading's predicate is false: a non-editor path reaches `import_image` |
| does that second path run in v1 | — | its receiver is a `MapConquest`/`MapConquestSea`, built for styles 0x18/0x19 only; `ConquestGame::build_conquest_game` writes them; the skirmish lobby's combo (`SetupWin::setup_combos@005bf490`, combo 0x31) offers 0x17 entries, styles 0–22; `set_map` draws 6–22 | **unreachable from the skirmish lobby** |

**Not settled.** The other writers of `info.map_style` that feed
`Game::init_rules_and_teams` → `set_map`'s pass-through → `new_map`:
`GameSpy::UpdateLobbyFromDTO@00962c70` (the online lobby; GameSpy is cut),
`ConsoleWin::run_cmd@007d6a70` (a console command writes it from a parsed
integer) and `ScenarioRead::import@009b1430` (a scenario file's stored style
byte, `pppCVar18[0x36]`). The console and the scenario file are the two
that could, on a reading, carry 0x18/0x19 into a non-CtW game. **FABLE:**
is scenario play (as distinct from the editor) inside v1, and can a
shipped scenario file store `CONQUEST_MAP`/`CONQUEST_SEA`? A grep of the
install's `scenario/` files' style byte answers the second half; the
first is a direction call, not a reading.

**So nothing moves for `force_continent_spacing`.** Both readings say
unreachable, but the first reading's predicate is wrong and the corrected
one has an open arm; per the item's rule, the disagreement parks (3859a).
It stays an open `NEVER` row.

**Falsifiers, both functions.** A `cover=1` trace entering `00694ab0`,
`0068c870`, `0068dba0`, `009a3f30` or `0068e6a0` from any lobby; for
`force_continent_spacing`, a shipped scenario whose style byte is 0x18 or
0x19, loaded through `ScenarioRead::import`.
